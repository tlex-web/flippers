<objective>
Close the last open part of G-04-21: the cradle (both Shifts held) across a force-clear. This uses the user's locked decision, option A (timing). Option B (accept as a residual) is not planned. Review IN-01, IN-02 and IN-03 ride along.

Root cause (binding, from 04-VERIFICATION.md gaps and 04-REVIEW.md WR-01):
- After forceClear, the marker repeatingShift names the Shift whose ignored auto-repeat arrived last. Windows typematic repeats only the LAST-pressed key, so in a cradle that is the last-pressed Shift.
- The player then re-presses that same Shift. ShiftLeft is still down, so Windows sends no keyup and flags the re-press repeat:true (VK_SHIFT merge). isSecondShiftPress(code) rejects it: code is not held, the other Shift is not held, and the marker names code itself.
- Neither bat can rise until every Shift is released. That is the original G-04-21 symptom.
- From events alone, an auto-repeat and a repeat-flagged re-press look the same. Only timing separates them: the typematic stream stops when the key is released, so a gap longer than the slowest repeat interval marks a fresh press.

Mechanism (per the verifier's option A, locked by the user):
1. KeyEventLike gains an optional timeStamp. A real KeyboardEvent already carries it, and attach() forwards the native event, so main.ts needs no change.
2. The repeat-ignore branch records the time of each ignored Shift auto-repeat beside the marker, in lastShiftRepeatAt.
3. isSecondShiftPress also accepts a repeat-flagged keydown of the marker's own code, once the gap since that recorded time exceeds SHIFT_REPEAT_GAP_MS (450 ms, a named exported constant).
4. A missing or non-finite timeStamp never triggers this rule.
5. IN-01: dropStaleShift clears the marker and its time whenever it drops both Shift codes. That makes the separate keyup reset in handleKeyUp redundant, so it is removed.

Threshold choice (researched):
- Microsoft's SystemParametersInfo docs give the Windows repeat speed as about 2.5 (KeyboardSpeed 0) to about 30 (KeyboardSpeed 31) repeats per second, so the slowest nominal interval is about 400 ms. 450 ms is above that, so a steady typematic stream never crosses it.
- The repeat delay is about 250 ms to 1 s (KeyboardDelay 0-3), and 500 ms is the default. This machine has KeyboardDelay 1 and KeyboardSpeed 31. Because 450 ms is below the default delay, a re-press missed under the gap is still taken on its own first auto-repeat at the default and longer delay settings.
- 500 ms or more would lose that late pickup at the default delay. 400 ms or less would misread the slowest nominal stream.

- **Hardware variance.** Microsoft states real repeat rates can deviate up to 20% from a linear scale. At KeyboardSpeed 0, a real interval near 480 ms could make a physically held Shift's steady stream count as a press after a clear.
