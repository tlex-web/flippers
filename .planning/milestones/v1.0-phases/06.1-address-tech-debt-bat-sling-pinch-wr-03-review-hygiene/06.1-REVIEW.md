### WR-01: Inlane sensor no longer reaches the funnel wall, so the drawn lane line, arrow lamp and glint sit off the lane

**File:** `src/table/spec.ts:292-296` (with `src/render/lamps.ts:374`, `src/render/static-layer.ts:440-446`, `src/render/effects.ts:137`)
**Issue:** `LEFT_FUNNEL` runs from (0.0, 4.5) to (0.6, 5.37).
- **Before:** at the old inlane line y = 4.95 the wall is at x ≈ 0.31. The sensor's left end (0.33, 4.95) was about 0.016 m from the wall (perpendicular), so the sensor spanned the lane, as its doc says.
- **After:** `INLANE_Y` = 4.6, where the wall is at x ≈ 0.069. The unchanged left end (0.33, 4.6) is now **0.215 m** from the wall.

Effects:
1. `static-layer.ts` strokes every `lane` element on the playfield. The inlane line now floats about 0.2 m away from the funnel wall on both sides of the table, a visible defect on the baked playfield.
2. The inlane arrow lamp (`lamps.ts:374`) and the inlane glint (`effects.ts:137`) are both placed at the sensor midpoint, x = 0.585. At the arrow's height (y = 4.37) the passage runs from the cabinet wall (x = 0) to the sling face (x = 0.86), centre 0.43. At the sensor line the passage is about 0.069–0.86, centre about 0.46. Either way the arrow sits about 0.12–0.155 m right of centre, crowding the sling.
3. The comment at line 292, "across the inlane from the funnel wall to the sling", is now false.

Scoring is not broken. A ball touching the funnel wall must have its centre at x ≥ ~0.31 when it crosses y = 4.6, which keeps it within 0.02 m of the sensor's end, so every passing ball still overlaps the sensor. The defect is visual and in the documentation. This project treats visual defects as bugs (CLAUDE.md).
**Fix:** Work out the sensor's left end from the funnel line at `INLANE_Y`, the same way `INLANE_Y` keeps the sling and sensor in step:
```ts
/** x of the left funnel wall at height y (linear on its one segment). */
function leftFunnelXAt(y: number): number {
  const [a, b] = LEFT_FUNNEL as [Vec2, Vec2];
  return a.x + ((b.x - a.x) * (y - a.y)) / (b.y - a.y);
}
const LEFT_INLANE: readonly Vec2[] = [
  { x: leftFunnelXAt(INLANE_Y) + 0.02, y: INLANE_Y }, // ≈ 0.09
  { x: 0.84, y: INLANE_Y },
];
```
Then update the pins on the midpoint x: `lamps.test.ts:552-568` and the arrow/sensor-midpoint test at `lamps.test.ts:619`, plus any `table-world`/`effects` pins. Check the arrow visually; it should sit centred in the lane.

### WR-02: The sling-pinch GREEN cases can pass vacuously because nothing checks that the ball reached and left the bat

**File:** `src/harness/sling-pinch.test.ts:118-127, 144-160`
**Issue:**
- `inlaneFlip` returns the highest *sustained* speed. A drained or missing ball counts as speed 0 (`b ? ... : 0`, line 121).
- `worstRatio` compares the result to `max(control, 1)`.
- The GREEN assertion is only `ratio <= 1.1`.

Suppose the slings were moved so they deflect, stall or trap the inlane drop before it reaches the bat. Every speed on the fixed table would then be near 0, and the GREEN case would pass without measuring a pinch. The RED control only shows the probe can see a pinch on the *old* geometry. It says nothing about whether the ball actually reaches the bat on the *new* table. The header claim at lines 31-32 ("the GREEN cases cannot pass merely because the probe went blind") is therefore only half true.
**Fix:** Add a positive liveness check on the fixed table. For example, require that across K_MIN..K_MAX most flips actually launch the ball:
```ts
let live = 0;
for (let k = K_MIN; k <= K_MAX; k++) {
  const v = inlaneFlip(table, id, k);
  if (v >= 0.5 * controlSpeed(id, k)) live++;
  worst = Math.max(worst, v / Math.max(controlSpeed(id, k), 1));
}
expect(live / (K_MAX - K_MIN + 1)).toBeGreaterThan(0.8);
```
Alternatively, count `ball-flipper` contacts during the raise window. Also assert that the ball still exists at every window step rather than mapping a missing ball to 0.

### WR-03: The kickback e2e now depends on a brute-force-searched player input, with the measured step numbers only in comments

**File:** `src/sandbox/game-e2e.test.ts:1014-1034, 1129-1144`
**Issue:**
- The live-composition kickback case now passes only because of one specific cradle: Slash, pressed 1 step after the kick, held until 30 steps past the window.
- That input was found by a deterministic search (comment, lines 1018-1028).
- The comment states measured values (kick at 534, unaided drain at 783, drain at 1294) that the test never asserts.

The contract under test is "one kickback save, same ball, next drain enters bonus". It is now tied to one exact ball path through the moved geometry. Any change to flipper torque, restitution or geometry will most likely fail with `drained off the cradle`, which points at the cradle rather than at the kickback rule. The comment also notes that an unaided kicked ball now drains at step 783, inside the original save window, where the CR-01 grace backstops it. That is a gameplay change caused by WR-03 and is recorded only in a test comment.
**Fix:** Keep the cradle, but turn the documented measurements into assertions, so drift fails with a diagnosable message. For example, add `expect(kickStep).toBe(534)` and assert the unaided-drain premise in a sibling run. Better, separate the two concerns:
1. A unit-level session test for "kickback, then a real drain past the window, enters bonus".
2. An e2e test that only proves the kick fires and sends the ball up-table.

Record the change to the unaided kickback outcome (it is now backstopped) in the phase summary, not only in a test comment.

### WR-04: Redundant check (already-defended-elsewhere): `keyLabel` code-point count before `PRINTABLE`

**File:** `src/ui/key-labels.ts:70-71`
**Category:** necessity
**Issue:** `PRINTABLE = /^[^\s\p{C}\p{M}]$/u` (line 60) is anchored, has one character class and uses the `u` flag. It therefore matches exactly one code point and rejects empty and multi-code-point strings. That makes the `codePoints(raw) !== 1` guard on line 70 redundant for every string input. `codePoints` is still needed on line 73 for the uppercase form, so only the guard on line 70 is unnecessary. The `typeof` check is also not needed for correctness, because `PRINTABLE.test(undefined)` tests the string "undefined" and returns false. It is harmless at a trust boundary, so it can stay.
**Fix:** Merge the two checks into `if (typeof raw !== "string" || !PRINTABLE.test(raw)) return null;`. Keep `codePoints` for the uppercase test, and update the doc to say `PRINTABLE` enforces the single code point.

### IN-01: `segToSegDist` returns a positive distance for crossing segments, so test (e) could miss an overlap

**File:** `src/table/table-world.test.ts:282-294, 438-441`
**Issue:** The helper's own doc says it is "Valid only for segments that do not cross". Test (e) relies on the physics never letting the bat axis cross a sling edge. A future spec that places a sling overlapping the bat's sweep could report the minimum of the four endpoint distances (possibly ≥ 0.45 m) instead of 0, and the clearance case would pass.
**Fix:** Return 0 when the segments properly intersect (two orientation cross-product sign tests) before taking the endpoint minimum.

### IN-02: Invisible raw Unicode literals in the keyLabel tests

**File:** `src/ui/key-labels.test.ts:96, 101, 103, 107, 145`
**Issue:**
- Lines 96, 101, 103 and 107 contain raw NBSP (U+00A0), ZWSP (U+200B), private-use (U+E000) and combining acute (U+0301) characters. They look like `" "`, `""`, `""` and `""`.
- Line 145 uses a plain ASCII space.
- The neighbouring cases (`"\u0007"`, `"\uD800"`, `"\u{1D538}"`) use escapes.

An editor, a paste or a normaliser can silently replace or drop these invisible characters. The test would then check something else (for example, the empty string) and still pass.
**Fix:** Use escapes: `"\u00A0"`, `"\u200B"`, `"\uE000"`, `"\u0301"`.
