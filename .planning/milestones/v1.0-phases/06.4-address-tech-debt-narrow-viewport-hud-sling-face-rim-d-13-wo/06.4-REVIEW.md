## Warnings

### WR-01: The `apply-view.test.ts` boot-call guard is vacuous, because the dpr handler's call satisfies it

**File:** `src/sandbox/apply-view.test.ts:89` (with no mutation case in `:117-167`)
**Issue:** `invocationViolations` treats `/^\s*applyView\(\);/m` as proof of the boot call. The `applyView();` statement inside `onDprChange` (main.ts:404, `      applyView();`) matches the same multiline regex. Deleting the real boot call at main.ts:398 therefore still passes the test titled "runs on boot, resize and dpr change". I verified this by removing `    applyView();` before the resize listener in a copy of the source: the regex still matched `"      applyView();"`. The mutation block has no "boot call removed" case, so nothing proves the guard has teeth. A missing boot call would leave the canvas at its default 300x150 and `data-hud` unset until the first resize, and no gate would catch it.
**Fix:** Anchor the check to the boot site, outside any handler, and add the mutation:
```ts
// invocationViolations
const outsideDpr = code.replace(braceBlock(code, code.indexOf("{", dpr)), "");
if (count(outsideDpr, "applyView();") < 1) out.push("no boot call");
// or, simpler and format-stable enough for this file:
if (!/applyView\(\);\s*window\.addEventListener\("resize", applyView\)/.test(code)) out.push("no boot call");

// mutation
it("boot call removed", () => {
  const s = m('    applyView();\n    window.addEventListener("resize", applyView);',
              '    window.addEventListener("resize", applyView);');
  expect(invocationViolations(s)).not.toEqual([]);
});
```

### WR-02: The side panel is measured empty at boot and never again, so wider HUD states consume the 16 px clearance

**File:** `src/sandbox/main.ts:386-389, 398` (HudView built only at `:417-424`, first written at `:581`). Related: `index.html:178-186`, `src/ui/hud.ts:161`
**Issue:** `applyView` decides side or bar from `hud.getBoundingClientRect().right`. Its contract is "keep the side panel only when the fitted canvas clears it by `HUD_SIDE_GAP_CSS`" (main.ts:18-22, view-transform.ts:160-167). It runs on boot, before `HudView` exists, so the panel it measures has the markup "0" score and an empty status line. After that it runs only on resize and dpr change. The side panel's width is not state-invariant:
- `.hud-status` is `white-space: nowrap` at 16 px bold with `letter-spacing: 0.12em`.
- The longest status, "GAME OVER · PRESS ENTER" (23 chars, which hud.ts:161 documents as the longest), is about 246 px in Consolas and about 265 px at 0.6 em (06.4-RESEARCH:240 uses the same figure).
- The panel the predicate sees is sized by the controls rows: 268 px outer, about 234 px content (06.4-UI-REVIEW measurement).

So on every game over, the panel grows about 10-30 px to the right of the edge the predicate checked. This is a font-metric estimate; no pixel measurement covers it, because the UI audit measured only the attract state. In the band where the side layout is chosen with less than that margin to spare (for example vh 900 with vw about 1080-1110), the 16 px gap shrinks to a few px or goes negative. The bar layout was designed to keep one size in every state (index.html:57-59), but the side layout got no equivalent guarantee. Any future longer status string makes this a real overlap of the table.
**Fix:** Make the side panel's width state-invariant so the boot-time measurement holds. Either reserve the widest status in CSS, for example `.hud-status { min-width: calc(23ch + 23 * 0.12em); }`, kept in sync with the "longest text" note in hud.ts:161 by a test like the one in hud-layout.test.ts. Or have `applyView` measure with the widest content: temporarily write `statusText("gameOver", 0)` into `#hud-status`, read `.right`, then restore. Add a test asserting that the reserved width covers every `statusText` code.

## Info

### IN-01: Bar row 2 (score and Mute) can overflow the bar below about 345 px viewport width

**File:** `index.html:72` (`grid-template-columns: 1fr auto`), `index.html:132-137` (`.hud-score` nowrap 32 px)
**Issue:** The `1fr` track's minimum is the score's min-content (nowrap), and the `auto` track holds "Mute [M] MUTED" (about 111-116 px). At 320 px the bar's content box is 278 px (320 - 16 margin - 2 border - 24 padding). A 7-digit score "1,234,567" (about 158-173 px), muted, needs about 281-301 px. The grid overflows the bar's right edge, the MUTED marker is pushed past it, and the page gains horizontal overflow. Research verified row 2 only at 375 px, and the UI audit measured 320 px with a score of 0, unmuted. The case is practically reachable only in a narrow desktop window with a keyboard.
**Fix:** `grid-template-columns: minmax(0, 1fr) auto;` plus a score size that scales (`font-size: clamp(24px, 9vw, 32px)` in bar mode), or `overflow: hidden; text-overflow: ellipsis` on the score cell.

### IN-02: The canvas's 1 px border is outside both layout predicates

**File:** `src/render/view-transform.ts:165-175`, `index.html:49`
**Issue:** `#stage` has `border: 1px solid`, so its box is `cssW + 2` by `cssH + 2`. `sideHudClears` uses `(vw - cssW) / 2`, so the guaranteed gap is 15 px, not the documented 16. `heightUnderBar` ignores the 2 px vertically and relies on the VIEW_FILL slack, which runs out when the height under the bar is below about 50 px. The grid test (view-transform.test.ts:145) has the same omission.
**Fix:** Add `export const STAGE_BORDER_CSS = 1` (asserted against index.html as with `HUD_BAR_GAP_CSS`) and use `(viewportW - view.cssW - 2 * STAGE_BORDER_CSS) / 2` and `viewportH - barH - HUD_BAR_GAP_CSS - 2 * STAGE_BORDER_CSS`.

### IN-03: The bar keeps "the last two children of `.hud-controls`", not "the Mute row"

**File:** `index.html:104` (with `:367-371`), `src/ui/hud-layout.test.ts:68-76`
**Issue:** `.hud-controls > :not(:nth-last-child(-n + 2))` is correct only while Mute is the final dt/dd pair. Adding any control row after Mute (for example a pause key) silently swaps which row the bar shows. The test checks only the selector text, not which elements it keeps.
**Fix:** Mark the row explicitly (`<dt data-bar-keep>Mute</dt><dd data-bar-keep>…`) and hide `.hud-controls > :not([data-bar-keep])`. Alternatively, add a hud-layout test asserting that the last `<dt>` in `#hud-controls` is "Mute".

### IN-04: The grid "never overlaps" test restates the predicate and cannot see runtime panel width

**File:** `src/render/view-transform.test.ts:136-149`
**Issue:** The side branch asserts `(vw - full.cssW) / 2 >= PANEL_RIGHT + HUD_SIDE_GAP_CSS`, which is the formula inside `sideHudClears`. It checks the implementation against a copy of itself, using a fixed `PANEL_RIGHT = 284`. The title "never lets the panel or the bar overlap the canvas" therefore claims more than the test can observe. It cannot catch WR-02 (the panel growing past 284) or IN-02 (the border).
**Fix:** Retitle it to "the predicate and the bar fit are consistent over a viewport grid", and cover the panel-width invariant separately (see the WR-02 fix).

### IN-05: The root-shot header and titles still overstate what the gate enforces

**File:** `src/harness/root-shot.test.ts:17-20, 36-37, 357`
**Issue:** The new Gate paragraph matches `classify()` and D-13. The intro sentence (lines 17-20, not changed this phase) still says a mid-bat-to-tip flip "must rise past its own slingshot into the upper field". The gate accepts cross shots that later strike their own sling, and up to `MAX_OPP_DOWN` flips that never clear. "Knocked back down" (line 37 and the `it` title) is counted as `!r.cleared` (line 268), which also includes a cross shot that simply fails to reach `CLEAR_Y` within `WINDOW_STEPS` without being knocked down.
**Fix:** Change the intro to "...must not meet its own slingshot first..." and rename "knocked down" to "not cleared within WINDOW_STEPS" in the header, the summary string and the title.

### IN-06: `SLING_RIM_LINE_M` duplicates a relation as a literal

**File:** `src/render/palette.ts:127-128`
**Issue:** The doc says "half of RUBBER_LINE_M", but the value is the literal `0.015`. If someone retunes `RUBBER_LINE_M`, the documented relation silently breaks.
**Fix:** `export const SLING_RIM_LINE_M = RUBBER_LINE_M / 2;`
