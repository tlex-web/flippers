## Summary

I reviewed the diff from `c0ee9b2` and read each file in full. The diff covers the sling trim to t = 0.28, the explicit `kickFace` designation (spec, resolver validation, `deriveKickFace`), and the new SHOT-CLEARANCE harness `root-shot.test.ts`. All 4 test files pass (100 tests) and `tsc --noEmit` is clean. I checked the geometry by hand. The corner (0.944, 4.102) lies exactly at t = 0.28 on the old hypotenuse. The face is 0.2656 m long, and the normal stays (0.9487, -0.3162). `FACE_STRIKE` (0.911, 3.973) is the face midpoint pushed 0.0095 m out along that normal. `mirrorPath` keeps path order, so `kickFace: 2` is correct for both slings. The resolver validation is correct, and so is every caller of `deriveKickFace` (rules, effects, static layer, renderer).

I found one blocker. It is in the gate, not the game. `root-shot.test.ts` classifies a flip by its *first* sling contact only. D-13, as written in CONTEXT, requires "no contact with its **own** bat's sling before" clearing. I ran a scratch copy of the harness that records any own-sling contact before clearing. On the current table it found a gated flip (bat 1, inlane k = 94, along = 0.436) that grazes sling 300, then hits its own sling 301, and never clears. The suite reports it as an "opposite-sling contact (knocked down)", so the phase-close claim "own-sling failures 0" does not hold under D-13 as written.

Measured on the current table: TABLE_SPEC gated 94, own 0, opposite 30 (2 down), kept 17/17, root strip clear 10/139. NO_SLING gives root strip clear 118/139.

## Critical Issues

### CR-01: Own-sling gate is weaker than D-13 and hides a measured own-sling knockdown

**File:** `src/harness/root-shot.test.ts:176-182` (classification), `:150-156` (doc claim)
**Issue:** The recorder returns as soon as `first` is set, and `ownTouched` is set only when that first contact is the own sling:

```ts
if (first !== null) return;
first = { id: e.elementId, x: e.point.x, y: e.point.y };
if (e.elementId === own) ownTouched = true;
```

D-13 (06.3-CONTEXT.md, Post-research amendments) defines the gate as "reach y ≤ 3.85 with vy < 0 within 60 steps, with no contact with its own bat's sling before that." The `FlipResult` doc says first-contact classification is what D-13 specifies, and it is not. A scratch copy of this harness tracked own-sling contact up to the clear. On TABLE_SPEC it reports:

- `bat 1 place=inlane k=94 along=0.436 first=300 ownLater cleared=false`. This flip is inside the gated band [0.25, 0.45]. It touches its own sling 301 and is knocked down, yet it is counted under `oppDown` and passes.
- Two more flips (bat 0 k=102, bat 1 k=96) do the same, but their along values are 0.465 and 0.462, so they are off-tip and ungated.

So the headline assertion "every kept flip … clears its own sling" is false on the shipped table. Any future change that makes a cross shot ricochet into its own sling is invisible, except through the coarse `MAX_OPP_DOWN` cap. That cap is set exactly at the measured value, and this flip uses one of its 2 slots.
**Fix:** Pick one and make the code and CONTEXT agree.
(a) Enforce D-13 as written: mark own contact on any own-sling event before the clear, independent of `first`:
```ts
let cleared = false; // hoist above the listener
router.register((e) => {
  if (!armed || cleared || e.elementKind !== "slingshot") return;
  if (e.elementId === own) ownTouched = true;
  if (first === null) first = { id: e.elementId, x: e.point.x, y: e.point.y };
});
```
This exposes the k = 94 flip as an own failure. The trim, the band or the decision then has to answer it.
(b) Amend D-13 to say explicitly that a flip whose first contact is the opposite sling is governed only by the cross-shot cap, even if it later strikes its own sling. Then correct the `FlipResult` doc and the test title so they stop claiming every kept flip clears its own sling.

## Info

### IN-01: Suite title claims root shots clear; measured root clearance is 10/139

**File:** `src/harness/root-shot.test.ts:356`
**Issue:** The `describe` says "root and mid-bat shots clear their own sling". Under D-03/D-06 the root strip (d < 0.25) is only measured. With slings, 10/139 root flips clear without sling contact, against 118/139 with no slings. Nothing guards that metric, so it could fall to 0/139 without any test failing. The title overstates what is proven.
**Fix:** Rename it to "mid-bat-to-tip shots (d in [0.25, 0.45]) clear their own sling". Optionally add a loose floor on `rootClear` (for example `>= 4`, the pre-trim value) so the root strip cannot quietly get worse than before the trim.

### IN-02: Rest-grid flips are gated on nominal d, not on the measured `along`

**File:** `src/harness/root-shot.test.ts:315-321`
**Issue:** Rest-grid flips are classified by their placement d (REST_D vs ROOT_REST_D). The ball droops for up to 10 steps first, though, and the actual `along` is never compared with [D_MIN, D_MAX]. The inlane sweep does check it (lines 325-332). The header says gating is by contact point d in the band. A d = 0.2 placement that rolls into the band goes ungated, and a d = 0.45 placement that rolls past the tip is gated.
**Fix:** Route rest flips through the same `along` banding as inlane flips, or document that the rest grid is gated by placement.

### IN-03: Endpoint clamp makes the trimmed obtuse corner a kick zone on the passive lower face; tuning comment is stale

**File:** `src/game/reactive-elements.ts:488-489` (with `src/game/tuning.ts:59-65`)
**Issue:** `distanceToSegment` clamps to the face endpoints. A contact on the passive lower face within about 0.049 m of the corner (0.944, 4.102) therefore passes `SLING_FACE_TOL`. Example: 0.03 m down the lower face with the 0.0095 m manifold offset gives a distance of about 0.031 m, so the sling kicks along the hypotenuse normal. The same clamp existed before the trim. After the trim, though, the corner is a 152° vertex sitting on the path that bat shots take, and segment 1 is the face those shots strike. The `SLING_FACE_TOL` comment ("the passive faces stay well outside it") is no longer true near that corner. No test covers a lower-face contact.
**Fix:** Add a slingshot-filter case for a lower-face contact (for example 0.1 m below the corner), and state the corner-zone behaviour in the tuning comment. If corner kicks are unwanted, use an unclamped projection with `0 <= t <= 1`.

### IN-04: Stale ball placement in the sling filter tests

**File:** `src/game/reactive-elements.test.ts:389,397`
**Issue:** `addBall(0, 1.15, 4.07)` dates from the pre-trim face. Projected onto the trimmed face, t is about 1.13, so the ball sits past the face's end. The kick math uses only velocity, so the assertions still hold, but the fixture no longer shows a ball on the face it strikes.
**Fix:** Place the ball at `FACE_STRIKE + (BALL_R - 0.0095) * n`, or derive it from `deriveKickFace(tableElement(300))`.

### IN-05: `spec.ts` sling doc uses pre-trim corner names

**File:** `src/table/spec.ts:285-297,305-309`
**Issue:** The doc still calls (0.944, 4.102) the "lower-right corner" and segment 1 the "lower face". After the trim that corner sits 0.5 m above the lower-left vertex (y 4.102 vs 4.6). Segment 1 is now a steep 0.505 m face pointing at the bat, and the triangle is a sliver: 18.4° at the top, 9.6° at the lower-left, 152° at the right. The 0.632 m clearance figure is also only asserted as `>= 0.45` in table-world test (e).
**Fix:** Rename the corners to "right corner" and "inner face" (or similar), and note the 9.6° lower-left spike so future edits do not treat it as a "lower face".

### IN-06: `kickFace` is enforced only at runtime, and indexes post-tessellation segments

**File:** `src/table/spec.ts:66-71`, `src/table/resolve.ts:236-247`
**Issue:** `kickFace?: number` is optional on every `PolylineSpec`. "Required on slingshots" and "rejected elsewhere" exist only as resolver throws, although the project uses TS so that config errors fail at compile time. The index also refers to resolved segments. For a sling path containing an `ArcNode`, the index depends on `ARC_CHORD_EPS`/`BALL_RADIUS_M`. A tuning change would silently retarget a different segment that is still in range, and the resolver cannot detect that. No sling uses arcs today.
**Fix:** Optionally split out a `SlingshotSpec` (`kind: "slingshot"`, required `kickFace`) in the `ElementSpec` union. Document or reject arc nodes on slingshots.

### IN-07: Impossible-state guard — silent skip of a face-less slingshot

**File:** `src/game/reactive-elements.ts:331-332` (and `:182`)
**Category:** necessity
**Issue:** Since 06.3, `resolve()` throws on any slingshot without a valid in-range `kickFace` (`resolve.ts:236-247`, `:260`). It also rejects every segment shorter than `MIN_VERTEX_SPACING` = 0.01 m (`resolve.ts:206-215`). So a slingshot from the real world can never reach `deriveKickFace(el) === null` or `faceLen === 0`. `if (!face) continue;` would silently build a slingshot that never kicks, instead of failing loudly. This rests on judgment, because `ReactiveWorld.getElements()` is a test seam and could be fed hand-built elements.
**Fix:** In the constructor, throw for a slingshot with no face (`throw new Error(\`slingshot ${el.id} has no kick face\`)`). That matches the resolver's fail-loud stance and keeps `deriveKickFace`'s null return for non-slingshot callers.
