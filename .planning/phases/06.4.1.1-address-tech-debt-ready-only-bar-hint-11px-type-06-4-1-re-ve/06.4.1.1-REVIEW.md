## Critical Issues

### CR-01: Bar hint flickers on bounce apexes during every weak-plunge fall-back (violates D-01 "only while the ball rests")

**File:** `src/game/game-session.ts:904-906` (signal), `src/ui/hud.ts:362` (consumer)
**Issue:** `isBallOnPlunger()` returns `activeRestingInZone()`, which is a single-step test: the center is in `PLUNGER_ZONE` and `|v| < PLUNGER_REST_SPEED_EPS` (0.05 m/s). After a weak release the ball falls back and bounces on the chute floor. At each bounce apex its speed crosses zero inside the zone (minY 5.6, rest y 6.2), so the test passes for a few steps and then fails as the ball drops again. Traced on the real table (same `makeGame` composition as `skill-shot-e2e.test.ts`, settle 120 steps, then hold and release):

| hold steps | isBallOnPlunger transitions after release (step: value, y, speed) |
|---|---|
| 0 | 180: true (y 6.095, v 0.047), 183: false, 207: true (v 0) |
| 10 | 229: true (y 6.047, v 0.029), 232: false, 270: true, 273: false, 282: true (v 0) |
| 40 (`WEAK_HOLD_STEPS`) | 377: true (y 5.857, v 0.015), 379: false, 439: true, 442: false, 456: true (v 0) |

Each false-true window is 2 to 3 fixed steps (17 to 25 ms). A 60 Hz frame runs 2 steps, so every 3-step window lands in at least one rendered `HudView.update`. "Hold Space to launch · ← → flip" therefore blinks once or twice on every fall-back. Real rest (exactly 0 m/s, as the `PLUNGER_REST_SPEED_EPS` doc says) follows 10 to 20 steps later. This is a visible flicker, and it contradicts D-01 ("only while the ball rests on the plunger"). The JSDoc's claim that the signal "needs no previous-step-idle guard" holds for the release step, but it misses the bounce apexes.
**Fix:** Debounce on the step clock in the session so it stays deterministic. Count consecutive resting steps in `tick()` and expose readiness only after a settle window that is longer than any apex window (the trace shows at most 3 steps; a served ball reads 0 m/s from step 0, so a short delay costs nothing at serve):
```ts
// tuning.ts
/** Consecutive resting steps before the bar hint shows (100 ms; bounce apexes rest <= 3 steps). */
export const PLUNGER_HINT_SETTLE_STEPS = 12;

// game-session.ts
private restSteps = 0;

tick(): void {
  this.step++;
  ...
  const atRest = this.activeRestingInZone();
  this.restSteps = atRest ? this.restSteps + 1 : 0;
  const resting = phase === "idle" && this.prevPlungerPhase === "idle" && atRest;
  ...
}

isBallOnPlunger(): boolean {
  return this.restSteps >= PLUNGER_HINT_SETTLE_STEPS && this.activeRestingInZone();
}
```
Reset `restSteps` on serve, re-serve and drain, then add the e2e assertion from WR-01. (The plunger release gate and the skill-shot reopen use the same single-step test, so a release at a bounce apex launches today. That predates this phase and is out of scope here, but the same counter could serve both.)

## Warnings

### WR-01: The "returns when the ball falls back" e2e test passes on the first bounce apex, not at rest

**File:** `src/sandbox/skill-shot-e2e.test.ts:484-487`
**Issue:** `runUntil(g, () => g.session.isBallOnPlunger())` stops at the first step the signal is true. For `WEAK_HOLD_STEPS` (40) that is step 377 after release: a bounce apex at y 5.857, speed 0.015, not the rest at step 456 (see the CR-01 trace). The follow-up assertions cannot tell these apart. `isRestingInZone(g.ball(), PLUNGER_ZONE)` is the same predicate `isBallOnPlunger()` just returned, so it is a tautology. `getPhase() === "idle"` and `firstSwitch() === null` hold at the apex as well. The test is green with the flicker present, so it gives no evidence that the ball "falls back to rest".
**Fix:** After the first true, require the signal to stay true and the ball to be at true rest:
```ts
runUntil(g, () => g.session.isBallOnPlunger());
for (let i = 0; i < 60; i++) {
  runSteps(g, 1);
  expect(g.session.isBallOnPlunger(), `step ${i} after first ready`).toBe(true);
}
const b = g.ball();
expect(Math.hypot(b.vx, b.vy)).toBe(0);
```
This fails on the current code and passes once CR-01 is fixed.

### WR-02: The presentation determinism replay no longer mirrors main.ts; a compensating test pins an unconsumed read

**File:** `src/sandbox/main.ts:426`, `src/sandbox/presentation.determinism.test.ts:282`, `src/ui/hud.test.ts:1292-1306`
**Issue:** `main.ts` now builds `HudView` with a sixth argument, the `#hud-hint` sink. `presentation.determinism.test.ts` says it "builds the `main.ts` composition", but it still constructs `new HudView(hudScore, hudBall, hudStatus, hudBest, hudBest)` with no hint sink. As a result, the hint attribute writes (the new per-frame DOM write path) never run in the bit-identical replay at 60 Hz, 144 Hz or with reduced motion. To make up for this, `hud.test.ts` adds "reads isBallOnPlunger() even with no hint sink, so the presented replay exercises it". That test fixes the behavior of calling a getter whose result nothing uses as a contract. It is a workaround for the composition drift, not a property of `HudView`. (`presentation.determinism.test.ts` is outside the listed scope, but the `main.ts` change in scope causes the drift.)
**Fix:** In `presentation.determinism.test.ts`, pass a recording `AttrSink` as the hint sink, matching `main.ts`. Add its write sequence to the presented `Outcome`, or assert it is non-empty so the run is non-vacuous. Then delete the "no hint sink" test in `hud.test.ts`. Optionally skip the `isBallOnPlunger()` read when `this.hint === null`.

## Info

### IN-01: "false before onStart" never reaches the NO_BALL guard

**File:** `src/game/game-session.test.ts:1669-1674`
**Issue:** Before `onStart()` the rig's `live` set is empty, so `getBalls()` returns no balls. `activeRestingInZone()` then returns false from the loop fallthrough, not from the `this.active === NO_BALL` guard. Removing the guard would still pass, so the test does not pin the "no ball in play" contract its name claims.
**Fix:** Make a ball exist while `active === NO_BALL`. For example, add an extra ball id at `SPAWN` (the rig's `extraBallIds`), or reach game-over after ball 3 drains with a stray ball still live, then assert false.

### IN-02: The type-floor scan misses a final declaration without a semicolon

**File:** `src/ui/hud-layout.test.ts:306`
**Issue:** `/font-size:\s*([^;]+);/g` only matches declarations that end in `;`. In CSS, `{ font-size: 10px }` (the last declaration, no semicolon) is valid, and this test would not see it. The same applies to the `font:` shorthand scan. The guard is meant to block any future sub-12 px size, and this gap lets one through.
**Fix:** Use `/font-size:\s*([^;}]+)[;}]/g` (and the same for `font:`).

### IN-03: The side-panel test anchors on HTML comment text

**File:** `src/ui/hud-layout.test.ts:378`
**Issue:** `markup.indexOf("<!-- End-of-ball bonus")` uses comment wording as a structural boundary. Rewording the comment breaks the test even though the DOM is unchanged.
**Fix:** Find the end of `#hud` structurally instead, for example by using `indexOf('id="hud-bonus"')` as the upper bound, since the bonus overlay is the next sibling.
