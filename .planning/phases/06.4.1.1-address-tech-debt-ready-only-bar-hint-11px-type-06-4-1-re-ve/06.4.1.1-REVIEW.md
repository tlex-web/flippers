## Summary

This is an incremental re-review of `git diff c448ab0 HEAD`, covering gap-closure plans 06.4.1.1-05 (the `restSteps` settle window and `PLUNGER_HINT_SETTLE_STEPS`) and 06.4.1.1-06 (the presented replay drives `#hud-hint`, the no-sink short-circuit in `HudView`, and the hud-layout test fixes).

I checked each of the six prior findings against the source. All six are fixed:

- **CR-01:** The settle window holds. Apex rest time is `2 * PLUNGER_REST_SPEED_EPS / IN_PLANE_GRAVITY` = 2 * 0.05 / 4.61 s, about 2.6 steps at 120 Hz. That fits the 3-step CR-01 trace and stays well under 12, including at the apex of the main fall-back.
- **Settle timing:** `tick()` counts from the pre-step snapshot and the live term reads the post-step snapshot. So "true" needs 13 consecutive resting snapshots, and it drops on the first frame after a release.
- **Count resets:** Every path that changes `active` resets the count or passes through `NO_BALL` first (`onStart`/`endBonus`→`serveBall`, `backstop`→`reServe`, `service` drain, ball-search forfeit via `service`).
- **Tests:** The five reviewed test files pass locally (255 tests).

I found no correctness or security defects. The remaining items are test-strength gaps, stale docs and one redundant reset.

## Info

### IN-01: The reduced-motion hint equality only compares how many times the hint was written

**File:** `src/sandbox/presentation.determinism.test.ts:675` (with the alternation check at `:644`)
**Issue:** `RecordingAttrSink` records only `name=value` / `-name` with no step number. The "not vacuous" case requires strictly alternating writes, and every run starts with the same first write (`-data-ready`). So the whole sequence follows from its length. `expect(p.hint).toEqual(q.hint)` then only checks that both runs wrote the hint the same number of times. A reduced-motion run that showed the hint on different steps would pass, which weakens the "changes nothing else" claim for the hint.
**Fix:** Record the step with each write, e.g. pass the session into the sink or push `${session.getStep()}:${name}=${value}`, so `toEqual` checks when the hint changed, not just how often.

### IN-02: Nothing tests the new "no sink, no read" contract

**File:** `src/ui/hud.ts:360-364`, `src/ui/hud.test.ts:117-119`
**Issue:** The `hud.ts` comment now says `isBallOnPlunger()` is "read only when a hint sink is wired", and the fix report says "a view with no sink never reads `isBallOnPlunger()`". The commit deleted `onPlungerReads` and the old opposite test, but added no test for the new behaviour. If someone removes the `this.hint !== null &&` prefix, no test fails.
**Fix:** Restore a read counter on `FakeSource` and add a case: a five-argument `HudView` with `state = "playing"` and `onPlunger = true` calls `update()` and expects `onPlungerReads` to be 0.

### IN-03: `HudSource.isBallOnPlunger` and `HINT_READY_ATTR` docs still describe the plain rest test

**File:** `src/ui/hud.ts:92`, `src/ui/hud.ts:96-98`
**Issue:** Both doc comments say "the ball in play rests on the plunger". Since D-10 the signal means "has rested for `PLUNGER_HINT_SETTLE_STEPS` consecutive steps and still rests". The `GameSession.isBallOnPlunger()` doc was updated, but the interface the HUD codes against was not, so a FakeSource author has the wrong model.
**Fix:** Change it to "The ball in play has settled on the plunger (rested `PLUNGER_HINT_SETTLE_STEPS` steps, still resting): the bar hint's ready signal (06.4.1.1 D-02, D-10)."

### IN-04: `tick()` runs the same rest scan twice per step

**File:** `src/game/game-session.ts:610-614`
**Issue:** Whenever the plunger was idle on this step and the last one, `activeRestingInZone()` runs twice in a row against the same snapshot: once for `resting` and once for `restSteps`. The second scan repeats the `getBalls()` loop for no reason. A later edit could also let the two reads drift apart without anyone noticing.
**Fix:**
```ts
const restingNow = this.activeRestingInZone();
const resting = phase === "idle" && this.prevPlungerPhase === "idle" && restingNow;
this.prevPlungerPhase = phase;
this.restSteps = restingNow ? this.restSteps + 1 : 0;
```
This keeps the same values, with no sim change.

### IN-05: Impossible-state guard: the serve and drain `restSteps` resets

**File:** `src/game/game-session.ts:472`, `src/game/game-session.ts:995`
**Category:** necessity
**Issue:** These two resets guard a state that can't happen.
- **Drain (`:472`):** It runs right after `this.active = NO_BALL` (`:471`). Until the next `tick()`, `isBallOnPlunger()` already returns false through the `NO_BALL` guard in `activeRestingInZone()` (`:691`). That next `tick()` then writes `restSteps = 0` (`:614`).
- **Serve (`:995`):** `serveBall()` is reached only from `onStart()` in `"game-over"` or from `endBonus()` in `"bonus"`. In both states `active === NO_BALL` and at least one `tick()` has already run, because `endBonus` can only run on a later `service()` than the drain. So `restSteps` is already 0 at both call sites.
- **Re-serve:** Only the `reServe()` reset (`:1012`) is load-bearing, which mutation M3 confirms.

The fix report calls the other two "defense in depth". That is a reasonable hedge against future call-order changes, but the field doc (`:288-290`) reads as if all three resets matter. This is Info, not Warning: the state is provably impossible today, but keeping the hedge is a scope call.
**Fix:** Either keep the resets and say in the field doc that only the re-serve reset is load-bearing, or remove the serve and drain resets. Removing them changes no step behaviour.

### IN-06: The BONUS-heading `not.toMatch` is now vacuous; the div-balance check does the work

**File:** `src/ui/hud-layout.test.ts:392-412`
**Issue:** `heading > bonus` (`:396`) and `hudEnd` is the `<div id="hud-bonus"` opening, so `hudEnd <= bonus`. The slice `[hudStart, hudEnd)` therefore ends before the first `class="hud-bonus-heading"`. `expect(hud).not.toMatch(/hud-bonus-heading/)` (`:411`) can only fail for some other spelling, such as a second class token. The case still has teeth through `closes === opens`. But it never checks that the heading sits inside the `#hud-bonus` overlay, even though the test name says so. A heading placed after the overlay closes would pass.
**Fix:** Also bound the overlay. Take the slice from `hudEnd` to its matching `</div>` (same open/close count walk) and assert that the heading index falls inside it. Drop or reword the redundant `not.toMatch`.
