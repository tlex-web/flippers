## Fixed Issues

### WR-01: The scan reads only jsdom's serialization, so markup jsdom drops but Chrome keeps (inside `<select>`) is never scanned

**Files modified:** `src/render/asset-free.test.ts`, `src/types/jsdom.d.ts`
**Commit:** c0294bc
**Applied fix:**
- **Two views.** `stripIconLink` now builds `new JSDOM(html, { includeNodeLocations: true })` and returns `StrippedHtml { serialized, raw }`.
  - `raw` is the `index.html` source with only the validated link's span cut out (`dom.nodeLocation(link)`: `startOffset`/`endOffset`).
  - Before the cut, the code checks that the location is not null or undefined and that the span is the `<link ...>` tag.
  - A new helper, `strippedSources(file, stripped)`, keys the two views as `<file> (serialized)` and `<file> (raw)`. Every caller scans both: the index.html scan, the strip assertions, the WR-02b row and the apple-touch-icon row.
- **Type declarations.** `src/types/jsdom.d.ts` gains only what the test uses:
  - the `includeNodeLocations?: boolean` option;
  - a `NodeLocation { startOffset; endOffset }` interface;
  - `nodeLocation(node: Node): NodeLocation | null | undefined`.
  - These match jsdom 31's `api.js`: it returns parse5 8's `sourceCodeLocation`, and throws when the option was not set. I checked the null and undefined cases: an implied `<head>` gives null, and a node created by `createElement` gives undefined.
  - The offsets index the raw input string, also with CRLF line ends and a leading BOM (probed).
- **The real-page test is tighter.** It now asserts that `raw` equals `index.html` with exactly the link's text cut out.
- **Why the serialized scan stays (decision).** Each view catches inputs the other misses, so both run:
  - The raw view catches markup jsdom's parser drops but the browser keeps (the select PoC).
  - The serialized view catches values that only take their scanned form after parsing. Character references are decoded (`href=&#x2f;&#x2f;cdn/x.css`, `u&#x72;l(`, `data&#x3a;image/png`), and unquoted values get quoted. The `data: URI asset` pattern needs that quote.
  - The existing WR-02b row now pins this. Its unquoted `href=data:image/png` hits `/index.html (serialized): data: URI asset`, and the row asserts that the raw view does NOT hit it. Dropping the serialized scan would fail that row.
- **New negative row: the select PoC.** This is "the raw scan catches assets jsdom drops from inside a `<select>` but browsers load". It is the reviewer's exact `<select>` line, inserted before `<main id="sandbox">` in the real `index.html`. The row asserts four things:
  - `stripIconLink` resolves (no structural rejection);
  - the serialized view holds the empty `<select aria-hidden="true" style="display:none"></select>`;
  - the raw view hits `img tag`, `CSS url() reference`, `image, audio or font file extension` and `remote URL in markup or CSS`;
  - the serialized view hits nothing.
- **Guard proven: the raw scan.**
  - With the raw scan disabled (scratch mutation: `raw: ""`), this row fails with `img tag: expected [] to include '/index.html (raw): img tag'`. Under that mutation the whole gate passes the PoC, as it did before this fix.
  - With the raw scan restored, the row passes.

### WR-02: A noscript inside `<template>` evades the noscript ban, so Chrome builds a second (PNG) icon link that jsdom sees as an attribute value

**Files modified:** `src/render/asset-free.test.ts`
**Commit:** de27bc9
**Applied fix:**
- **The check.** `doc.querySelector("noscript")` is now `doc.querySelector("noscript, template")`. The message is now `index.html must hold no noscript or template element`.
- **Docstrings.** The file header's HTML bullet and the `stripIconLink` docstring now explain two things:
  - why a template is rejected: querySelector does not search template contents, and Chrome can close the template from inside the noscript's raw text;
  - why nesting needs no recursion: the outermost template is a real element of the document tree.
- **Existing noscript row.** Updated to the new message.
- **New it.each.** "a noscript inside a template is rejected: %s" has two rows. Each inserts `<template><noscript><p title="</noscript></template>HIDDEN<template>"></p></noscript></template>` before `<style>` in the real `index.html`. Each row then asserts:
  - (a) jsdom finds exactly one icon link (the real one) and no noscript in the document tree;
  - (b) whether the raw-scan `icon link` pattern can see the hidden link at all;
  - (c) the `data: URI asset` pattern cannot see it (its href is unquoted);
  - (d) `stripIconLink` rejects it with the template-ban message.
- **Row 1: the reviewer's exact PoC (the PNG icon link).**
  - What it asserts: rejection by the template ban (assertion d).
  - The row also asserts that the raw `icon link` pattern does match the hidden link.
  - Guard-disabled check (scratch mutation back to `querySelector("noscript")`): `stripIconLink` resolves and the row fails. The full post-WR-01 scan then reports only `["/index.html (raw): icon link"]`.
  - So with WR-01 in place, the raw scan is a second, independent catch for this exact input. Before WR-01 (the serialized scan alone), nothing caught it, which matches the reviewer's and the orchestrator's re-run.
- **Row 2: the hidden link written as `<link title='>' rel=icon type=image/png href=data:...>`.**
  - This is the variant the reviewer warned the raw scan alone cannot catch. The row asserts that the `icon link` pattern does NOT match it, because the quoted `>` stops `[^>]*`.
  - Guard-disabled check: `stripIconLink` resolves, the row fails, and the full two-view scan reports `[]`. The gate passes it entirely.
  - So the template ban is the only guard for this row.
- **Not verified by me in a browser.** I did not run Chrome on row 2. That Chrome builds a live icon link from it rests on two earlier results: the reviewer's Chrome 158 result for row 1's template escape, and the earlier WR-02 quoted-`>` PoC (`title='>'` keeps the link a real element). Either way, the row is rejected structurally.

### IN-01: `stop-color` in `PAINT_ATTRS` is unreachable, and the docstring claims it is checked

**Files modified:** `src/render/asset-free.test.ts`
**Commit:** ef3dac1
**Applied fix:**
- **Removed, not kept.** `"stop-color"` is gone from `PAINT_ATTRS`, and `checkIconElement`'s docstring now says "every fill and stroke value". I chose removal because no allowed element can carry it: `ICON_ELEMENTS` holds no gradient or `<stop>`, and `ICON_ATTRS` does not list `stop-color`.
- **Comments.** `PAINT_ATTRS` now documents that each member must also be in `ICON_ATTRS`. The "off-palette stop-color" row has a comment explaining that it is rejected as `element <stop>`.
- **New invariant test.** "every paint attribute is allowlisted, so the paint check can read it" asserts `ICON_ATTRS.has(attr)` for every `PAINT_ATTRS` member.
  - With `stop-color` put back (scratch mutation), the test fails with `stop-color: expected false to be true`.
  - So an unreachable paint attribute cannot come back silently.
