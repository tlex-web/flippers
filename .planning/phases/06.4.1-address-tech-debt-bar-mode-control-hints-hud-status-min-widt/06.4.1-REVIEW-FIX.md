## Fixed Issues

### WR-01: Raw tab/LF/CR in the href is removed by the browser's URL parser but not by the validator, so split tokens get through the gate

**Files modified:** `src/render/asset-free.test.ts`
**Commit:** 862f3db
**Applied fix:** Took the review's sturdier option: a positive allowlist of raw href characters.
- `ICON_HREF_CHARS = /^[A-Za-z0-9%\-_.!~*'() =/:]*$/` holds letters, digits and `%` escapes. It also holds the characters `encodeURIComponent` leaves unescaped (`-_.!~*'()`), so the existing `iconLink()` rows still reach their own checks. Finally it holds the space, `=`, `/` and `:` that the real favicon writes literally. That is every raw character the real href uses. `,` from the review's example was dropped, because the payload does not need it.
- `stripProceduralIcon` runs the check after the existing `&` check. That keeps the earlier "HTML character references" rows reporting their own message.
- The docstring explains the URL-parser stripping layer.

Three new hand-built rows put a raw character into an otherwise percent-encoded payload: `st<LF>yle=`, `on<TAB>load=` and `u<CR>rl(`. Building them by hand keeps `iconLink()` from encoding the character. Each row also asserts two things: that deleting the tab, LF and CR gives back the clean encoded payload (what the browser actually decodes), and that `PROCEDURAL_ICON` still matches the link.

With the guard disabled, all three payloads passed the validator ("expected [Function] to throw an error"). The first draft of the `url(` row used `url(#f)`, which the off-palette hex check caught anyway. I changed it to `url(#0b0420)` so the row proves a real bypass.

### WR-02: Attributes are still a denylist, so a `filter` presentation attribute recolors the icon off-palette with no flagged token

**Files modified:** `src/render/asset-free.test.ts`
**Commit:** 21ecd60
**Applied fix:** Added an `ICON_ATTRS` allowlist: `xmlns`, `viewBox`, `width`, `height`, `x`, `y`, `rx`, `ry`, `cx`, `cy`, `r`, `d`, `fill`, `stroke`, `stroke-width` and `transform`.
- It covers every attribute in the real favicon (`xmlns`, `viewBox`, `width`, `height`, `rx`, `fill`, `cx`, `cy`, `r`, `stroke`, `stroke-width`) and in the existing positive row (`ry`, `d`). It leaves out every opacity attribute (IN-03).
- The scan `/[\s'"]([^\s'"=/>]+)\s*=/g` runs after the element check, so the SMIL rows keep their `element <set>` messages. It reads only names that sit directly before `=`, so values such as `xmlns`'s URL, `viewBox` numbers and `d` path data do not produce false positives. The real favicon and the positive row both pass.
- The scan uses a whitespace-or-quote boundary, which is stricter than the review's whitespace-only one. It also catches a malformed `fill='#0b0420'filter='…'`.
- The `validateIconSvg` docstring now says that both elements and attributes are allowlisted.

New negative rows:
- `filter='invert(1) drop-shadow(0 0 2px red)'` (the review's payload)
- `opacity='0.3'`
- a quote-adjacent `filter`

With the attribute check disabled, all three pass the validator. Under the review's whitespace-only regex, the quote-adjacent row also passes, which shows why the stricter boundary is needed.

### IN-01: "no rgba value" assertion is tautological (carried from the previous review)

**Files modified:** `src/render/asset-free.test.ts`
**Commit:** f17756e
**Applied fix:** Replaced the tautology with a check that can fail.
