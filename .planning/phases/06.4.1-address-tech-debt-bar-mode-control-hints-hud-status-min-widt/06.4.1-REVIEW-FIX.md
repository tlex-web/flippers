## Fixed Issues

### WR-01: A shape can still paint SVG's initial black. A fill value padded with non-ASCII whitespace passes the gate, but the browser rejects it.

**Files modified:** `src/render/asset-free.test.ts`
**Commit:** 0ccbc44 (href layer), c11462d (paint check)
**Applied fix:**
- **Href layer (0ccbc44).** `ICON_HREF_CHARS` now admits `%` only as an ASCII escape, `%[0-7][0-9A-Fa-f]`. The decoded SVG can no longer hold U+00A0, U+FEFF, U+3000 or any other non-ASCII character. The `ICON_HREF_CHARS` and `stripProceduralIcon` docstrings and the gate's error message now say this.
- **Paint check (c11462d).** `String.prototype.trim()` is replaced with an ASCII-only strip, `/^[ \t\n\r\f]+|[ \t\n\r\f]+$/g`, which is CSS whitespace. The paint check now reads the value the way the browser does. The `validateIconSvg` docstring and an inline comment record the reason.
- **Other `.trim()` calls.** The validator has no other `.trim()` calls. The `\s` classes in the other regexes also match Unicode whitespace, but they only go wrong in the strict direction (more denylist hits, fewer accepted names). One exception: the fill-presence parser would read `<rect\u00A0fill=...>` as a rect that has a fill. That text is not well-formed XML (U+00A0 cannot separate attributes), so the browser shows a broken image, not black paint. After 0ccbc44 the href cannot deliver that text anyway. I left those classes unchanged.
- **The existing favicon and test rows still pass.** The real favicon href in `index.html` uses only `%23`, `%3C` and `%3E`. Every existing `iconLink()` row encodes an ASCII-only SVG, so `encodeURIComponent` emits only `%00`-`%7F` there.
- **New rows, href layer (0ccbc44).** Two hand-built hrefs splice `%C2%A0` or `%EF%BB%BF` next to `%23f72585`. Each row first checks that the href decodes to `GOOD_SVG` with the padded fill, then asserts the `outside ICON_HREF_CHARS` message. With the old `%[0-9A-Fa-f]{2}` pattern restored, both rows fail. Before c11462d they passed the whole validator. After c11462d the paint check would also catch them, with a different message. These rows test the href guard's own message, not that the payload gets through every other check.
- **New rows, paint check (c11462d).** These call `validateIconSvg` directly, past the href layer. U+00A0 before `#f72585`, U+FEFF after it, and U+3000 before `none` each throw `paint fill=`. With `.trim()` restored, all three fail. The palette-hex, element, attribute and fill-presence checks do not catch these payloads, so the paint check is the only guard. One positive row checks that `fill=' #f72585 '` (padded with ASCII spaces) still passes both `validateIconSvg` and `stripProceduralIcon`. With no trimming at all, that row fails.

### IN-01: A well-formed `%XX` escape that is not valid UTF-8 still throws a bare `URIError`, contrary to the new docstring

**Files modified:** `src/render/asset-free.test.ts`
**Commit:** 0ccbc44 (the same commit as WR-01's href layer)
**Applied fix:**
- **Pattern.** A one-byte ASCII escape always decodes, so `decodeURIComponent` can no longer throw on any href that passes `ICON_HREF_CHARS`.
- **Docstring.** The `ICON_HREF_CHARS` docstring now names the non-UTF-8 class (`%FF`, `%C3%28`, an encoded surrogate) and explains why every remaining escape decodes. The earlier claim that every malformed escape gets the named message is now true.
- **Error message.** It now reads "a raw character, or a bad or non-ASCII % escape, outside ICON_HREF_CHARS".
- **New rows.** `%FF`, `%C3%28` and `%ED%A0%80` are added to the existing bad-escape `it.each`. Each asserts that `decodeURIComponent(raw)` throws `URIError` and that the gate throws the `outside ICON_HREF_CHARS` message. With the old pattern restored, all three fail with a bare `URIError: URI malformed`.
