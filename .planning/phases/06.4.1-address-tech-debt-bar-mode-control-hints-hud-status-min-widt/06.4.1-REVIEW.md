I probed with a scratch copy of `stripProceduralIcon` / `validateIconSvg`, taken straight from the file, and rendered the payloads that passed as `<img src="data:image/svg+xml,...">` in headless Chrome.

**What the two fixes close:**
- **IN-01 (bare `URIError`).** Closed. Every escape left decodes to one ASCII byte, and so do the literal characters, so `decodeURIComponent` cannot throw. The `%FF`, `%C3%28` and `%ED%A0%80` rows fail with the gate's own message.
- **WR-01 (non-ASCII whitespace around a fill).** Closed. U+00A0, U+FEFF and U+3000 can no longer reach the decoded SVG. The CSS-only trim rejects them on the direct `validateIconSvg` path as well.
- **Other ASCII control escapes are harmless.** NUL, VT and DEL inside a fill are rejected by the paint check. A form feed (`%0C`) passes the gate, but FF is not a legal XML 1.0 character, so the browser shows a broken image rather than off-palette paint. That matches the stance already accepted for XML that is not well-formed. A raw trailing space is cut off by the URL parser but only after `</svg>`. `xmlns=''` on a shape removes that shape and adds no paint.

**What is still open:** The new escape range still admits `%0A` and `%0D`. A fill value that holds a decoded LF or CR is never read by the paint check, and it renders off-palette (WR-01 below). This gap existed before 0ccbc44. c11462d added `\n` and `\r` to the trim set as if the check read those values, but the trim never runs on them, and the new positive test only uses spaces.

## Warnings

### WR-01: A paint value holding a raw LF or CR bypasses the paint check and renders any color

**File:** `src/render/asset-free.test.ts:276-277` (paint regex), `347` (`ICON_HREF_CHARS` admits `%0A` / `%0D`), `677-681` (the positive test only covers spaces)

**Issue:**
- **Why the check misses it.** The paint regex captures the value with `(.*?)\2`. In JavaScript, `.` does not match `\n` or `\r`. So a value such as `fill='\nred'` produces no match at all, and the paint check never sees the attribute. The CSS-whitespace trim added in c11462d (`[ \t\n\r\f]`) never runs on these values, so the LF and CR in it do nothing.
- **Why the other checks miss it.**
  - The `#hex` check finds no `#`.
  - `fill`, `stroke` and the shape elements are all on the allowlists.
  - The fill-presence check uses `'[^']*'`, which does span the newline, so it sees a `fill` and passes.
- **What the browser does.** XML attribute-value normalization turns the LF or CR into a space, and CSS trims it, so the browser paints `red`.
- **How it gets in.** `ICON_HREF_CHARS` admits `%0A` and `%0D` (`%[0-7][0-9A-Fa-f]`). A percent-encoded LF is not removed by the URL parser; only raw tab, LF and CR are. So it reaches the decoded SVG.
- **The result.** The gate's promise at lines 15-19 and 243-252 that every fill and stroke is `none` or a palette hex does not hold. The same bypass also lets a broken value (for example `fill='r\ned'`) paint SVG's initial black.

**Evidence:**
- **The gate passes these.** A scratch copy of `stripProceduralIcon` returned PASS for each of these links, built with `encodeURIComponent` and added to `GOOD_SVG`:
  ```
  <rect width='32' height='16' fill='\nred'/>
  <rect y='16' width='32' height='16' fill='\rlime'/>
  <circle cx='16' cy='16' r='14' fill='none' stroke='\nyellow' stroke-width='3'/>
  <rect width='8' height='8' fill='\ncurrentColor'/>
  ```
- **Chrome paints them off-palette.** Rendered as images in headless Chrome:
  - a solid red half;
  - a solid lime half;
  - a yellow ring;
  - a black square (`currentColor` resolves to black).

  The control favicon rendered as expected.

**Fix:** Do both of the following.

1. Make the paint regex read across line breaks, by splitting on the quote rather than using `.`:
   ```ts
   // line 276
   for (const m of svg.matchAll(/\b(fill|stroke|stop-color)\s*=\s*(?:'([^']*)'|"([^"]*)")/gi)) {
     const raw = m[2] ?? m[3] ?? "";
     const value = raw.replace(/^[ \t\n\r\f]+|[ \t\n\r\f]+$/g, "").toLowerCase();
     if (value !== "none" && !PALETTE_HEX.has(value)) {
       throw new Error(`icon SVG paint ${m[1]}=${raw} is not none or a palette.ts hex`);
     }
   }
   ```
2. Narrow the href escapes to printable ASCII. The favicon needs no control characters, and this removes LF, CR, tab, FF and NUL from the decoded SVG entirely:
   ```ts
   // line 347: `%` only as a printable-ASCII escape (%20-%7E)
   const ICON_HREF_CHARS = /^(?:[A-Za-z0-9\-_.!~*'() =/:]|%(?:[2-6][0-9A-Fa-f]|7[0-9A-Ea-e]))*$/;
   ```
   If you apply this, update the docstring at lines 333-346 to match.

Add negative rows to the test file:
- `validateIconSvg(withElement("<rect width='32' height='32' fill='\nred'/>"))` must throw `paint fill=`. This direct call proves fix 1.
- The same SVG via `stripProceduralIcon(iconLink(...))` must throw `outside ICON_HREF_CHARS`. This proves fix 2.

Also extend the positive test at lines 677-681 with `fill='\n#f72585\n'`, so the LF and CR part of the trim is exercised (only through a direct `validateIconSvg` call, once fix 2 applies).
