## Warnings

### WR-01: The scan reads only jsdom's serialization, so markup jsdom drops but Chrome keeps (inside `<select>`) is never scanned

**File:** `src/render/asset-free.test.ts:419` (`return dom.serialize()`), `482` (the index.html scan takes only that string), `34-36` (the docstring says the serialized remainder is what gets scanned)

**Issue:**
- **What the gate assumes.** Before this change, PATTERNS ran over the raw `index.html` text minus the regex-stripped link. Now they run only over `dom.serialize()`. That assumes jsdom's tree holds everything the browser's tree holds.
- **Where that breaks.** parse5 8.1.1 still uses the old "in select" insertion mode. It drops every start tag inside `<select>` other than option, optgroup, input, script and template.
- **What Chrome does.** Chrome 158 uses the current HTML spec's relaxed select parsing (customizable `<select>`). It keeps `<img>`, `<div>`, `<link>` and the rest as real elements, and it fetches them.
- **Why the scan misses it.** The dropped markup is absent from the serialization, so no pattern can see it.

This is a regression from the migration. The old raw-text scan hit `<img` on the same input.

**Evidence:**
- **The input.** I added this line before `<main id="sandbox">` in the real `index.html`:
  ```html
  <select aria-hidden="true" style="display:none"><img src=stars.png><div style="background:url(stars.jpg)"></div><link rel=stylesheet href=//cdn.example/x.css></select>
  ```
- **The gate passes it.** The scratch `stripIconLink` + `scan` returns PASS. jsdom's body serialization is just `<select aria-hidden="true" style="display:none"></select>`.
- **Chrome loads it.** The select's `innerHTML` holds the `img`, `div` and `link`. `document.images` lists `.../stars.png`, and `querySelectorAll("link").length` is 2. Chrome fetches the image even though the select is hidden.
- **What gets past.** Three patterns are masked here: `img tag`, `CSS url() reference` and `remote URL in markup or CSS`.

**Fix:** Keep the serialized scan, and also scan the raw source with only the validated link's own source span cut out. The union is strictly stronger than either scan alone. jsdom exposes the span through `includeNodeLocations`:
```ts
const dom = new JSDOM(html, { includeNodeLocations: true });
// ... all existing checks ...
const loc = dom.nodeLocation(link);
if (!loc) throw new Error("icon link has no source location");
const raw = html.slice(0, loc.startOffset) + html.slice(loc.endOffset);
link.remove();
return { serialized: dom.serialize(), raw }; // scan both
```
- **Type declarations.** Add `includeNodeLocations?: boolean` and `nodeLocation(node: Node): { startOffset: number; endOffset: number } | null` to `src/types/jsdom.d.ts`.
- **Callers.** Scan both strings at lines 482 and 994. Make the line 541-544 assertions check both.
- **Verified in the scratch copy.** I joined the two strings into one scan. The real `index.html` still returns PASS. The PoC now fails on img tag, CSS url(), file extension and remote URL.
- **New test row.** Add the PoC above as a negative row.

### WR-02: A noscript inside `<template>` evades the noscript ban, so Chrome builds a second (PNG) icon link that jsdom sees as an attribute value

**File:** `src/render/asset-free.test.ts:402-404` (`doc.querySelector("noscript")`), `21-24` and `389-392` (the docstring says rejecting noscript closes the scripting-flag differential)

**Issue:**
- **Why the check misses it.** `querySelector` does not descend into a template's content, which is a separate DocumentFragment. So a noscript nested in `<template>` is never found.
- **Template contents still parse differently.** In "in template" mode a `<noscript>` start tag is handled by the "in body" rules.
  - **In Chrome (scripting on),** it becomes a raw text element that ends at `</noscript>`. A following `</template>` then closes the template, and the parser goes back to "in head". So the markup after it is live head content.
  - **In jsdom (scripting off),** it is an ordinary element, so the same markup stays inside a `<p title="...">` value.
- **Why the scan misses it.** `serialize()` writes the value with `<` and `>` escaped, so neither the `icon link` pattern nor the `data:` pattern can match.

**Evidence:**
- **The input.** I added this line after the real favicon link (before `<style>`):
  ```html
  <template><noscript><p title="</noscript></template><link rel=icon type=image/png href=data:image/png;base64,iVBORw0KGgoAAAANSUhEUgAAABAAAAAQCAIAAACQkWg2AAAAFklEQVR4nGP4z8BAEmIY1TCqYfhqAADe3/8R2b3rLAAAAABJRU5ErkJggg==><template>"></p></noscript></template>
  ```
  The trailing `<template>` swallows the leftover `"></p>...` in Chrome, so nothing visible leaks into the page.
- **The gate passes it.** The scratch copy returns PASS: one icon link found, no noscript found, zero pattern hits. The serialized line is `<template><noscript><p title="&lt;/noscript&gt;&lt;/template&gt;&lt;link rel=icon type=image/png href=data:image/png;...&gt;&lt;template&gt;"></p></noscript></template>`.
- **Chrome builds two icon links, both in `<head>`:**
  ```
  [{"rel":"icon","type":"image/svg+xml","href":"data:image/svg+xml,%3Csvg xmlns='http://","parent":"HEAD"},
   {"rel":"icon","type":"image/png","href":"data:image/png;base64,iVBORw0KGgoAAAANSU","parent":"HEAD"}]
  ```
  This is the exact state the carve-out forbids. The "two icon links" and "data:image/png" rows assert it is rejected.
- **The control case.** The same payload without the `<template>` wrapper is rejected with "index.html must hold no noscript element". So the template is the whole bypass.

**Fix:** `index.html` has no template either. Reject it alongside noscript, rather than recursing into template contents:
```ts
if (doc.querySelector("noscript, template")) {
  throw new Error("index.html must hold no noscript or template element");
}
```
- **Why this covers nesting.** A top-level `<template>` is a real element in the document tree, so `querySelector` finds it. Nested templates are then covered too.
- **Verified in the scratch copy.** With this check, the real `index.html` still returns PASS and the PoC throws.
- **Comments and tests.** Update the docstrings at lines 21-24 and 389-392. Add the PoC as a negative row next to the line 987 noscript row.
- **Why the WR-01 fix is not enough on its own.** Its raw scan catches this exact PoC, because the raw text holds `<link rel=icon`. But the raw text also allows the old quoted-`>` trick: `<link title='>' rel=icon ...>` inside the title value dodges the non-quote-aware `icon link` pattern. So this check is still needed.

### IN-01: `stop-color` in `PAINT_ATTRS` is unreachable, and the docstring claims it is checked

**File:** `src/render/asset-free.test.ts:233`, `268-269`
**Issue:**
- **Why it never runs.** `stop-color` is not in `ICON_ATTRS` (lines 207-223), and `<stop>` is not in `ICON_ELEMENTS`. So the attribute loop at lines 281-286 throws on any `stop-color` before the paint loop can read it. The "off-palette stop-color" row (line 632) shows this: it is rejected as "element <stop>", not by the paint check.
- **The misleading docstring.** `checkIconElement`'s docstring says "every fill, stroke and stop-color value is none or a palette.ts hex". That suggests a gradient path that does not exist.

**Fix:** Drop `"stop-color"` from `PAINT_ATTRS` and from the docstring. Or keep it with a comment that it only matters if `stop` is ever allowlisted.
