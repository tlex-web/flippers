## Warnings

### WR-01: The icon-link placement and span-equality guards have no test; a comment claims an independent rejection that is never asserted

**File:** `src/render/asset-free.test.ts:499-501, 522-529, 1163-1165`
**Issue:** 134adf5 added two guards to `stripIconLink`:
- `link.namespaceURI !== XHTML_NS || link.parentElement !== doc.head` → "icon link must be an HTML <link> in head";
- `tag.startOffset !== loc.startOffset || tag.endOffset !== loc.endOffset` → "icon link source span is not its <link> tag".

No test asserts either message. Grep finds both strings only at their `throw` sites. The WR-01 PoC test (1166-1184) asserts only `"index.html element <svg>"`, because `checkIndexElements` runs first and throws before the placement guard is reached. Yet the comment at 1164-1165 says the placement guard "rejects the same page on its own". If someone deletes or breaks either guard, every test still passes.

The placement guard can still be reached past INDEX_ELEMENTS. An HTML icon link moved into `<body>` passes `checkIndexElements` and is caught only by `parentElement !== doc.head`. So the untested guard is the only defence on a reachable path.
**Fix:** Add direct tests that bypass INDEX_ELEMENTS:
```ts
it("the placement guard rejects an HTML icon link in body", async () => {
  const start = indexHtml.indexOf("<link");
  const end = indexHtml.indexOf("/>", start) + 2;
  const link = indexHtml.slice(start, end);
  const html = (indexHtml.slice(0, start) + indexHtml.slice(end)).replace(
    '<main id="sandbox">',
    `${link}\n    <main id="sandbox">`,
  );
  await expect(stripIconLink(html)).rejects.toThrow("icon link must be an HTML <link> in head");
});
```
For the SVG PoC, either assert the placement message on its own (for example by exporting a variant without the allowlist, or by calling the guard helper directly), or reword the comment at 1164-1165 to say the guard is not exercised there.

### WR-02: CSS escapes in allowed `<style>` / `style=` content evade every CSS asset pattern

**File:** `src/render/asset-free.test.ts:77-81, 118-123, 36-48`
**Issue:** The gate scans `<style>` blocks and `style` attributes only with regexes, in both the serialized and raw views. `style` is in INDEX_ELEMENTS, so this content is allowed. CSS decodes escapes inside identifiers and at-keywords:
- `u\72l(` is a `url(` token (CSS Syntax §4.3.4: "consume an ident-like token" compares the escape-decoded name to "url").
- `@\69mport` is `@import`.

Neither the jsdom serializer nor the raw view decodes CSS escapes. Checked in a scratch run of the gate's regexes:
- `<style>.a{background:u\72l(//cdn.example/bg)}</style>` → 0 pattern hits;
- `<style>@\69mport "//cdn.example/x";</style>` → 0 hits;
- `<div style="background:u\72l(//cdn.example/bg)">` → 0 hits.

This is the CSS version of the character-reference bypass (06.4.1-REVIEW WR-02, seventh pass). 134adf5 says INDEX_ELEMENTS "keeps every such element out", but that holds only for parse divergences in rejected elements, not for escapes inside allowed `style` content. The new header (36-48) therefore overstates what the gate guarantees for index.html CSS. The same gap applies to every scanned `src/**/*.css`. The gap predates this phase, but this diff rewrote the doc text that claims coverage.
**Fix:** Pick one (D-09 favours the first):
1. Narrow the doc comment: state that CSS content is regex-scanned only and that CSS escapes (`\hh`) are not decoded. Record this as an accepted limit of a gate that targets accidental assets.
2. Or reject CSS escapes in scanned CSS. Add a pattern, `{ name: "CSS escape in stylesheet", re: /<style[\s\S]*?\\[0-9a-f]|style\s*=\s*["'][^"']*\\/i, sample: "<style>a{b:u\\72l(x)}</style>" }`, and an equivalent check for `.css` files (`/\\[0-9a-fA-F]/`). index.html and the project CSS use no backslash escapes today.

### IN-01: The presented replay builds HudView without a hint sink, and a unit test pins an unobservable read instead

**File:** `src/sandbox/presentation.determinism.test.ts:282`, `src/ui/hud.test.ts:1292-1306`
**Issue:** The presented determinism replay constructs `new HudView(hudScore, hudBall, hudStatus, hudBest, hudBest)` with no sixth argument. Its write-on-change and determinism assertions therefore never cover the `data-ready` writes.

The test "reads isBallOnPlunger() even with no hint sink, so the presented replay exercises it" compensates by pinning an implementation detail: `HudView` must call the getter even when it has nowhere to write. That read has no observable effect, and the assertion locks in wasted work. It also passes only because the fixture is `playing` with status `none`; for any other state the `&&` short-circuits and the getter is never read.
**Fix:** Pass a `CountingElement` as the hint sink in the presented replay and include its write count in the replay comparison. Then drop the read-count test, or replace it with a write-count assertion on the real replay.
