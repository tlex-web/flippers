## Summary

This re-review covers `git diff d3647dc HEAD -- src/render/asset-free.test.ts`, which holds five commits: 862f3db (WR-01), 21ecd60 (WR-02), f17756e (IN-01), 7b58cea (IN-02) and 7ba0b88 (IN-03). I read the whole file and checked it against the real favicon in `index.html:7-11`. `npx vitest run src/render/asset-free.test.ts` passes 53 of 53 tests.

The five fixes close what they target:
- **WR-01 (raw href characters).** `ICON_HREF_CHARS` holds only printable ASCII that the URL parser leaves alone inside a `data:` opaque path. Raw tab, LF, CR, `&`, `#` and `?` are all rejected. Percent-encoded controls (`%0A` and so on) reach the XML layer as whitespace or invalid characters, where they either split a name into a disallowed one or break well-formedness. Leading and trailing space stripping by the URL parser cannot build a token. I found no remaining gap between what the validator reads and what the browser reads at this layer.
- **WR-02 (attribute allowlist).** XML well-formedness requires whitespace before every attribute and `name S? = S? value` for each one. So `/[\s'"]([^\s'"=/>]+)\s*=/g` sees every real attribute name, and text inside a value only adds names, which makes the check stricter. Namespaced names (`xlink:href`, `xmlns:x`, `xml:space`) are rejected. Non-ASCII whitespace that JavaScript's `\s` matches (for example NBSP) is not XML whitespace, so it makes the SVG malformed rather than hiding a name.
- **IN-01.** The rgba assertion can now fail: `WALL_GLOW` is required to be present.
- **IN-02.** The duplicate test is gone.
- **IN-03.** `opacity`, `fill-opacity` and `stroke-opacity` are left out of `ICON_ATTRS`, and each has a negative row.

One soundness gap is still open, and it is the one the allowlists cannot see: **an attribute that is absent**.
- **The gap.** SVG's initial `fill` is black. A shape with no `fill` therefore paints `#000000`, which palette.ts does not hold. The validator passes that shape, and the suite's own positive row does exactly this.
- **Evidence.** I confirmed it with a scratch copy of `stripProceduralIcon`, which returned PASS for `<rect width='32' height='32'/>`.
- **Severity.** As in the earlier passes, an SVG loaded as an image is sandboxed, so this is an RND-01 gate-soundness defect, not a runtime vulnerability.

Notes that are not findings:
- **WR-01 rows now have two guards.** The three hand-built rows (lines 550-568) are now also caught by `ICON_ATTRS`, either as `yle` / `load` or as the disallowed `filter`. The fix report's statement that "with the guard disabled, all three payloads passed" was true at 862f3db but has been stale since 21ecd60. The rows still check that their guard exists, because they assert the `outside ICON_HREF_CHARS` message.

## Warnings

### WR-01: A shape with no `fill` renders in SVG's default black, which is off-palette, and the validator (and its own positive row) admits it

**File:** `src/render/asset-free.test.ts:226-282` (`validateIconSvg`), `464-470` (positive row), `15-19` (gate docstring)
**Issue:**

*Cause.* The palette checks only run over paint that is written down:
- The paint regex (line 253) inspects `fill=`, `stroke=` and `stop-color=` values that are present.
- The `#hex` scan (line 259) inspects hex literals that are present.

Nothing requires a shape to declare its fill. The initial value of the SVG `fill` property is `black`. So any `rect`, `circle`, `ellipse` or `path` that has no `fill` attribute, and no `<g fill=...>` ancestor, paints `#000000`. palette.ts holds no `#000000`: its darkest colors are `#05061a` and `#0b0420`.

*Effect.* With no splitting, no encoding and no unlisted name, `stripProceduralIcon(iconLink(...))` returned PASS in a scratch copy for both of these:

```
<rect width='32' height='32'/>
<path d='M0 0h32v32H0z'/>
```

Each one paints a full black square over the icon. That breaks the promise at lines 15-19 ("drawn only from palette.ts colors") and the docstring of `validateIconSvg` ("a static, palette-colored drawing").

The suite already encodes the bypass as expected behavior. The row "admits every allowlisted element with palette paint" (line 467) adds `<path d='M0 0h1v1z' stroke='#f72585'/>`, which has a magenta stroke and an implicit black 1x1 fill.

**Fix:** Require an explicit `fill` on every painted shape. That is stricter than inheritance, but it is easy to check without a parser, and the real favicon already sets `fill` on every shape. Run the check after the element allowlist, so unknown tags keep their own message:
```ts
/** Shapes that paint with the initial (black) fill unless they declare one. */
const ICON_SHAPES: ReadonlySet<string> = new Set(["rect", "circle", "ellipse", "path"]);

// After the element loop: every shape's open tag must declare its fill
// (SVG's initial fill is black, which palette.ts does not hold).
for (const m of svg.matchAll(/<([a-z]+)\b([^>]*)>/g)) {
  if (ICON_SHAPES.has(m[1] ?? "") && !/\sfill\s*=/.test(m[2] ?? "")) {
    throw new Error(`icon SVG <${m[1]}> has no fill (SVG's default black is off-palette)`);
  }
}
```
Change the positive row's path to `<path d='M0 0h1v1z' fill='none' stroke='#f72585'/>`. Add negative rows for a fill-less `rect` and a fill-less `path`, both expecting `"has no fill"`.

## Info

### IN-01: A malformed `%` escape in the href fails with a bare `URIError` instead of a named gate fault

**File:** `src/render/asset-free.test.ts:299, 335`
**Issue:**
- **What happens.** `ICON_HREF_CHARS` admits `%` on its own, so a stray `%` or a `%zz` (from a hand edit or a bad re-encode) gets past the allowlist. `decodeURIComponent` then throws `URIError: URI malformed` (I confirmed this in a scratch copy).
- **Impact.** The gate still fails closed. But the failure names neither the icon nor the rule, unlike every other path through `stripProceduralIcon`.
- **A second difference.** The browser's percent-decoder leaves an invalid `%zz` as literal text and does not throw. So this is also a place where the validator and the browser read the input differently, although the difference is harmless.

**Fix:** Allow `%` only before two hex digits. Then the allowlist message covers this case and the docstring stays accurate:
```ts
const ICON_HREF_CHARS = /^(?:[A-Za-z0-9\-_.!~*'() =/:]|%[0-9A-Fa-f]{2})*$/;
```
