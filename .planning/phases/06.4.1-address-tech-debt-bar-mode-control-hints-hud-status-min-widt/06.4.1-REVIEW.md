- 74462cd: the paint regex now reads quoted values across line breaks.
- 02f6350: `ICON_HREF_CHARS` admits only printable-ASCII escapes (`%20` to `%7E`).

I read the whole file and checked it against the real favicon in `index.html`. `npx vitest run src/render/asset-free.test.ts` passes 79 of 79 tests.

I probed with a scratch copy of the file. It is the real code with only the vite-only imports and globs swapped out, run under Node 26 type stripping. Payloads that passed were loaded in headless Chrome to see how the browser parses them.

**Previous WR-01 (a paint value holding LF or CR): closed at both layers.**
- **Href layer.** Every decoded byte is now printable ASCII, so the decoded SVG holds no tab, LF, CR, FF, NUL or DEL. The real favicon uses only `%3C`, `%3E` and `%23`, so it is still admitted.
- **SVG layer.** `(?:'([^']*)'|"([^"]*)")` captures the whole value up to its own closing quote. I also checked whether an earlier match could swallow a real `fill`/`stroke` keyword so it is never checked: that keyword would have to sit inside the earlier match's captured value, and a captured value that passes is only `none` or a hex, so this cannot happen.
- **The new rows test what their names claim.** The fixer's guard-off runs (5 failures with the old regex, 11 with the old range) agree with my reading.

**No new defect in the two fix commits.**

**What is still open:** the carve-out at the HTML layer. `stripProceduralIcon` assumes the text `PROCEDURAL_ICON` matches is a standalone `<link>` element. It never checks this. As a result the browser can show a raster icon while the gate validates an SVG href that the browser throws away (WR-01). WR-02 is a related bypass in the `icon link` and `data: URI asset` patterns. Those patterns date from phase 05, but the carve-out's own claim and test ("every other icon link ... still fails") now rely on them. Fixing WR-01 alone leaves an equally easy route through WR-02, so treat the two as one decision: fix both, or record the HTML side of the gate as a tripwire that does not hold against deliberate tampering.

**Necessity:** I read the rubric (`necessity-review.md`). The paint check's `\t\n\r\f` trim can no longer be reached through `stripProceduralIcon`. It is a deliberate second layer, though, with its own direct tests, so it is not a necessity finding.

## Warnings

### WR-01: The procedural icon link can be merged into a preceding open tag, so the browser's favicon is an unvalidated raster

**File:** `src/render/asset-free.test.ts:335-336` (`PROCEDURAL_ICON` is not anchored to a tag boundary), `379-397` (`stripProceduralIcon`), `15-21` (the docstring promises "every other icon link ... still fails")

**Issue:**
- **What the check assumes.** `PROCEDURAL_ICON` matches `<link rel="icon" ...>` anywhere in the text. `stripProceduralIcon` validates that match's href and then deletes the match. It never checks that the `<link` starts a new tag.
- **What the browser does.** If an earlier tag is still open, the HTML tokenizer reads `<link` as a junk attribute name of that earlier tag. It then reads `rel`, `type` and `href` as more attributes of the same element. Duplicate attributes are dropped and the first one wins. So an earlier unquoted `type=` and `href=` replace the validated ones, while `rel="icon"` is taken from the stripped text.
- **Why the scan misses it.** After stripping, the leftover text is `<link type=image/png href=data:image/png;base64,...`. It holds no `rel=icon`, so the `icon link` pattern does not fire. It has no quote before `data:`, so the `data: URI asset` pattern does not fire either.

**Evidence:**
- **The gate passes it.** With the scratch copy of `stripProceduralIcon` + `scan`, the real `index.html` returns PASS. So does this edit of it, which adds one line before the real favicon link:
  ```html
  <title>Flippers</title>
  <link type=image/png href=data:image/png;base64,iVBORw0KGgoAAAANSUhEUgAAABAAAAAQCAIAAACQkWg2AAAAFklEQVR4nGP4z8BAEmIY1TCqYfhqAADe3/8R2b3rLAAAAABJRU5ErkJggg==
  <link
    rel="icon"
    type="image/svg+xml"
    href="data:image/svg+xml,%3Csvg ... (the real, valid payload)"
  />
  ```
- **Chrome builds a PNG icon link.** Headless Chrome (`--dump-dom`) builds exactly one icon link:
  ```
  {"rel":"icon","type":"image/png","href":"data:image/png;base64,iVBORw0KGgo...","attrs":["type","href","<link","rel"]}
  ```
  The validated `type` and `href` are dropped as duplicates. The page's favicon is the PNG.
- **Which promise breaks.** This is the case the test at lines 769-775 says is not admitted ("a data:image/png icon link is not admitted").

**Fix:**
- **The check.** In `stripProceduralIcon`, require the match to start at a tag boundary: the text before it, back to the last `>`, must be whitespace only.
  ```ts
  // after the matches.length check, before reading raw
  if (!/(?:^|>)\s*$/.test(html.slice(0, m.index))) {
    throw new Error("procedural icon link must start a new tag (it is inside an open tag)");
  }
  ```
- **Verified in the scratch copy.** The real `index.html` still returns PASS, and the edit above now throws. Every existing row that uses `iconLink()` matches at index 0 or after `\n` that follows a closed tag, so those rows are unaffected.
- **Why a `>` inside quotes cannot fool it.** Suppose the `>` is inside a quoted value of the earlier tag, and the procedural link sits inside that open value. The browser's element then takes no `rel` from the stripped text, because it is value text. The payload cannot supply one either, since `rel=` fails the `ICON_ATTRS` check. So it gets no icon.
- **New test row.** Add a row that puts `<link type=image/png href=data:image/png;base64,iVBORw0KGgo=\n` in front of `iconLink(GOOD_SVG)` and expects the new message.

### WR-02: A quoted `>` before `rel` hides an icon link from the `icon link` pattern, and an unquoted `data:` URI hides from the `data:` pattern

**File:** `src/render/asset-free.test.ts:73-77` (`icon link` pattern), `118-122` (`data: URI asset` pattern), `15-21` (the carve-out docstring relies on both)

**Issue:**
- **Where they come from.** Both patterns date from phase 05. 06.4.1 made them load-bearing for the carve-out: the docstring says that after stripping, "every other icon link, icon file and `data:` URI still fails". The tests at lines 759-775 assert this too.
- **Gap in the `icon link` pattern.** It is `<link\b[^>]*\brel...`. Its `[^>]*` stops at a `>` inside a quoted attribute value. HTML does not end a tag there, so `<link title='>' rel=icon ...>` is still an icon link.
- **Gap in the `data: URI asset` pattern.** It needs a quote or backtick before `data:`, so an unquoted `href=data:image/png;...` is not seen.
- **No carve-out needed.** This route has nothing to do with the carve-out.

**Evidence:**
- **The gate passes it.** The scratch copy returns PASS for the real `index.html` with this line added before `</head>`:
  ```html
  <link title='>' rel=icon type=image/png href=data:image/png;base64,iVBORw0KGgo...>
  ```
- **The browser shows it.** In HTML the title value ends at its closing quote, and `rel=icon` is a real attribute. So the browser shows this PNG as the favicon.

**Fix:**
- **Patterns.** Make both patterns quote-aware:
  ```ts
  // icon link: skip whole quoted values while looking for rel
  re: /<link\b(?:[^>"']|"[^"]*"|'[^']*')*\brel\s*=\s*["']?[^"'>]*\bicon\b/i,
  // data: URI asset: also after `=`, `(` or whitespace, not only after a quote
  re: /(?:["'`=(]|\s)data:(image|audio|font|video)\//i,
  ```
- **Checked.** I ran both against all 49 non-test `src` files plus the stripped `index.html`: 0 hits. They still hit:
  - the PoC above;
  - `<link href=data:image/png;base64,... rel=icon>`;
  - the existing samples (`rel="icon" href="favicon.ico"`, and the image, audio and font `data:` samples).

  The "raw index.html still trips" test at line 500 still holds, because the real link is quoted. Add the PoC line as a negative row.
- **If you choose not to fix this.** State in the docstring at lines 7-27 that the HTML side of RND-01 is a tripwire against mistakes, not against deliberate tampering. In that case, drop WR-01 for the same reason.
