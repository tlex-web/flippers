## Summary

**Scope.** `git diff d9993d8 HEAD -- src/render/asset-free.test.ts src/types/jsdom.d.ts` covers the three fix commits. I read the whole test file against the real `index.html`. jsdom is 31.0.1 and parse5 is 8.1.1. The suite passes 105 of 105.

**Method.** Each PoC was run in a scratch copy of the repo: `src`, configs and a modified `index.html`, with `node_modules` linked to the project's. The real test file was unchanged, and the command was `npx vitest run src/render/asset-free.test.ts`. Each page that passed was then served from a local Node server that logs every request, and loaded with `chrome.exe --headless=new --dump-dom` (Chrome 158.0.8127.37).

**What holds.**
- **Raw-span offsets.** The offsets are correct with a leading BOM and with CRLF line endings. parse5 offsets index the original string; I probed both directly. `.gitattributes` also pins LF.
- **HTML link span.** For an HTML-namespace `<link>`, the span is exactly the start tag. A stray `</link>` is left in the raw view, where it does no harm.
- **Splicing.** Cutting a start tag can only join the text on either side. That can create new matches (false positives) but cannot remove a match lying wholly outside the span.
- **The two views together.** They are at least as strong as either one alone, because `scan()` takes the union.
- **de27bc9 and ef3dac1** are correct.
- **`.d.ts` additions.** They match jsdom 31. `nodeLocation` returns `impl.sourceCodeLocation` (null when the parser implied the node, undefined for a node created by script), and the constructor throws a `TypeError` for `includeNodeLocations` with XML (`api.js:72-80`, `api.js:212-215`).

**Two gaps found, both reproduced end to end** (gate PASS, and Chrome fetches the asset):
- **WR-01.** The new span check does not prove the span is the link's start tag. A link in the SVG namespace spans its whole subtree.
- **WR-02.** The raw view that is meant to close the `<select>` divergence uses the old regexes. A character-reference spelling inside a `<select>` gets past both views.

**Severity.** Both are rated Warning, as the earlier passes rated equivalent bypasses: they are RND-01 gate-soundness defects in a test-only gate. Neither can make the test runner touch the network.

## Warnings

### WR-01: An SVG-namespace icon link takes its whole subtree out of both views, and the span check passes it

**File:** `src/render/asset-free.test.ts:431`, `src/render/asset-free.test.ts:452-461`

**Issue:** `querySelectorAll("link")` matches a `link` element in any namespace, and nothing checks `link.namespaceURI`. In foreign content, `<link>` is an ordinary SVG element and holds children. parse5 then gives it a location that runs past the start tag:
- to its `</link>`, or
- when an ancestor's end tag closes it implicitly, to the end of its last child.

Probed directly: `<svg><link rel=icon href=a><script>…</script></link></svg>` gives the span `<link rel=icon href=a><script>…</script></link>`.

The new check at 457 tests only that the span starts with `<link` and ends with `>`. That span passes, so the comment's claim at 454-455 ("the span must be the link's own start tag") is not enforced. Line 460 then cuts the whole subtree out of the raw view, and line 461's `link.remove()` removes it from the serialized view too. Anything inside the link is invisible to every pattern.

**Reproduced.** I deleted the real `<link rel="icon" …/>` from `<head>`, then added this line before `<main id="sandbox">`, with the real favicon href unchanged:

```html
<svg width="0" height="0"><link rel="icon" type="image/svg+xml" href="data:image/svg+xml,%3Csvg …(real favicon)…"><script>new Image().src = "http://127.0.0.1:8765/hit.png";</script><g/></svg>
```

The trailing `<g/>` makes the implied-close span end in `/>`. That also satisfies the hard-coded `indexOf("/>")` assertion at 600-603.

- **Gate:** the RND-01 scan (line 529) and the carve-out test (line 591) both PASS. 104 of 105 tests pass. The one failure is the WR-01 PoC fixture at 1027, which assumes the icon link follows `<title>`, so a real edit would only need that fixture rewritten.
- **Chrome 158:** `GET /hit.png`. The hidden SVG `<script>` runs, and it could hold any `fetch`, `new Image` or `@import`. Chrome also sends `GET /favicon.ico`, because the page has no HTML icon link, so the "validated" icon is never the favicon at all.

**Fix:**
- Pin the icon link to an HTML element in `<head>` before validating it.
- Cut the start tag's own span rather than the element's span.
- Add `startTag` to the `.d.ts`: parse5's `ElementLocation.startTag` is a `Location` with `startOffset` and `endOffset`.

```ts
const XHTML_NS = "http://www.w3.org/1999/xhtml";
// ...after the icons.length check:
if (link.namespaceURI !== XHTML_NS || link.parentElement !== doc.head) {
  throw new Error("icon link must be an HTML <link> in head");
}
// ...
const loc = dom.nodeLocation(link);
const tag = loc?.startTag;
if (!loc || !tag || tag.endOffset !== loc.endOffset) {
  throw new Error("icon link source span is not its <link> tag");
}
```

```ts
// src/types/jsdom.d.ts
export interface NodeLocation {
  readonly startOffset: number;
  readonly endOffset: number;
  /** Elements only: the start tag's own span. */
  readonly startTag?: { readonly startOffset: number; readonly endOffset: number };
}
```

Add a regression row that runs this PoC and expects the namespace or head rejection.

### WR-02: The raw view does not close the `<select>` divergence; a character-reference spelling inside a select passes both views

**File:** `src/render/asset-free.test.ts:43-47`, `src/render/asset-free.test.ts:436-438`, `src/render/asset-free.test.ts:1056-1084`

**Issue:** c0294bc covers markup that parse5 drops inside `<select>` (Chrome keeps it) by running the old PATTERNS over the raw source. The old regexes have the blind spot that the parser migration was meant to remove: a URL spelled with character references. That spelling was covered only by the serialized view (doc comment at 40-42), and the serialized view never sees select contents. Neither view sees the combination. The select test at 1062 proves only the regex-visible spelling, so the claim at 43-47 that the raw view "catches markup jsdom's parser drops but a browser keeps" is stronger than what it enforces.

**Reproduced.** I added this line before `<main id="sandbox">` in an otherwise unchanged `index.html`:

```html
<select aria-hidden="true" hidden><link rel=stylesheet href=http&#58;//127.0.0.1:8765/x&#46;css><div style="background:u&#114;l(http&#58;//127.0.0.1:8765/bg&#46;png)">x</div></select>
```

- **Raw view:** no pattern matches. `href=http&#58;//` is not `href=//` or `href=http://`, `u&#114;l(` is not `url(`, and `&#46;png` is not `.png`.
- **Serialized view:** it holds an empty `<select>`.
- **Gate:** the full file PASSes, 105 of 105.
- **Chrome 158:** keeps both elements, and `--dump-dom` shows `href="http://127.0.0.1:8765/x.css"`. The server logs `GET /x.css`, a remote stylesheet load that could pull in `@font-face` or `url()` assets.

This is the same class as the noscript/template ban (a jsdom-vs-browser parse divergence), and `index.html` holds no select.

**Fix:** Reject `select` along with `noscript` and `template`, instead of relying on the regex view to model it. Keep the raw view as defence in depth.

```ts
if (doc.querySelector("noscript, template, select")) {
  throw new Error("index.html must hold no noscript, template or select element");
}
```

- Update the doc comments at 21-26, 43-47 and 416-426.
- Change the test at 1062 to expect the rejection.
- Add a row with the character-reference PoC above.
- If some other parse5-vs-Chrome divergence turns up later, the regex-only raw view will have this same blind spot again, so prefer a structural ban each time.
