## Warnings

### WR-01: Favicon validator decodes percent-escapes but not HTML character references, so entity-encoded payloads get through the RND-01 gate

**File:** `src/render/asset-free.test.ts:223-232` (also `PROCEDURAL_ICON` at ~213)
**Issue:** `stripProceduralIcon` captures the raw HTML attribute text (`[^"]*`) and runs only `decodeURIComponent` before `validateIconSvg`. A browser's HTML tokenizer decodes character references in attribute values before it reads the `data:` URL, so the validator checks different text from what the browser renders. Reproduced (scratch copy of the validator, result `PASS`):

```
<svg xmlns='http://www.w3.org/2000/svg' ...>&lt;image &#x68;ref=&apos;&#x68;ttps://evil.example/x.png&apos;/&gt;</svg>
```

The browser decodes this to `<image href='https://evil.example/x.png'/>`. The `<image`, `href` and `http` checks all miss it. The `#hex` check misses it too, because `&#x68;` gives `#x…`, which `/#[0-9a-f]+/` does not match (only decimal references such as `&#104;` are caught, and only by accident). The same trick gets `&lt;script&gt;`, `&lt;style&gt;` and so on past the checks. Because the link is stripped before the PATTERNS scan, no other check sees it. The test-file header (lines 15-19) promises that the carve-out admits only a validated palette-only SVG, and this breaks that promise.
**Fix:** Reject any HTML character reference in the captured value. That is simpler and safer than writing an HTML decoder. Also add the negative case to the `it.each` table:
```ts
function stripProceduralIcon(html: string): string {
  // ...count check as now...
  const raw = m[1] ?? "";
  if (raw.includes("&")) {
    throw new Error("icon href must not contain HTML character references");
  }
  validateIconSvg(decodeURIComponent(raw));
  // ...
}
// it.each row (build the link by hand; iconLink() would percent-encode the &):
// ["an HTML character reference", ..., "HTML character references"]
```

### WR-02: Paint check is a denylist that misses SMIL `<set>`/`<animate>`, so off-palette colors pass

**File:** `src/render/asset-free.test.ts:165-177, 185-206`
**Issue:** The doc comment says "every fill, stroke and stop-color value is none or a palette.ts hex". The check only inspects `fill=`, `stroke=` and `stop-color=` attributes. `<set attributeName='fill' to='red'/>` and `<animate attributeName='stroke' values='red;lime' dur='1s'/>` both return PASS in the reproduction. Neither the paint regex nor the `#hex` scan looks at `to`, `values`, `from` or `by`, and `ICON_FORBIDDEN` has no SMIL entry. Chrome and Firefox run SMIL in SVG images, including favicons. So the "palette only" guarantee can be bypassed, and an animated favicon could get in unnoticed. This is the general weakness of a forbidden-token list: any SVG element or attribute nobody thought of is allowed by default.
**Fix:** Switch to an allowlist of elements and attributes. The favicon needs very few:
```ts
const ICON_ELEMENTS = new Set(["svg", "rect", "circle", "ellipse", "path", "g"]);
for (const m of svg.matchAll(/<\/?\s*([a-zA-Z][\w:-]*)/g)) {
  if (!ICON_ELEMENTS.has(m[1]!)) throw new Error(`icon SVG element <${m[1]}> is not allowed`);
}
```
The minimum fix is to add `<set`, `<animate` (which also covers `<animateColor`, `<animateTransform` and `<animateMotion`) and `<feflood` to `ICON_FORBIDDEN`, with matching `it.each` rows.

## Info

### IN-01: "no rgba value" assertion is tautological

**File:** `src/render/asset-free.test.ts:340-345`
**Issue:** `PALETTE_HEX` is built (around lines 147-151) by filtering on `/^#[0-9a-f]{6}$/i` and lowercasing, so `[...PALETTE_HEX].every((v) => /^#[0-9a-f]{6}$/.test(v))` can never fail. It does not prove anything about the rgba exports in palette.ts.
**Fix:** Assert something with teeth instead. For example, that a known rgba export (`palette.WALL_GLOW`) is absent: `expect(PALETTE_HEX.has(palette.WALL_GLOW.toLowerCase())).toBe(false)`. Or drop the line.

### IN-02: Three tests run the same real-index.html validation

**File:** `src/render/asset-free.test.ts:271-274, 330-333, 356-358`
**Issue:** The main scan test, "carries exactly one procedural SVG icon link…" and "the real index.html still passes the payload validation" all call `stripProceduralIcon(indexHtml)`. The third adds nothing that the other two don't already check. The duplication makes one fault fail three tests and hides which one is the intended guard.
**Fix:** Remove the "still passes the payload validation" test, or fold it into the "exactly one" test.

### IN-03: `WORST.bonus` is a back-solved magic number, not a derived bound

**File:** `src/ui/hud-layout.test.ts:37-48, 263-265`
**Issue:** `bonus: 9_999_999_999_999` was picked so that `BONUS 9,999,999,999,999` comes to exactly 23 code points, tying "GAME OVER · PRESS ENTER". The `widest === 23` test is therefore driven entirely by `gameOver`. The bonus row only checks that no one picked a number larger than this one. "Any reachable bonus is far below" is stated but not tied to the bonus tuning, so a future bonus change cannot fail this test.
**Fix:** Derive the bonus worst case from the bonus tuning constants (the maximum per-row value times the cap) where one exists. Otherwise, note in the comment that the side panel grows to the right for a bonus over 13 digits, which is acceptable.
