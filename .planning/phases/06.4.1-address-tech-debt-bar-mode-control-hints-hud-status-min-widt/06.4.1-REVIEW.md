## Summary

This re-review covers `git diff 58cee7a HEAD -- src/render/asset-free.test.ts`, which holds two commits: 09fb06f (WR-01, every shape must declare its own `fill`) and 735a50b (IN-01, `%` allowed only as a hex escape). I read the whole file and checked it against the real favicon in `index.html`. `npx vitest run src/render/asset-free.test.ts` passes 60 of 60 tests.

I probed the edge cases with a scratch copy of `validateIconSvg` / `stripProceduralIcon`, then rendered the passing payloads in headless Chrome.

**The quote-aware tag parser holds up:**
- **Tag forms.** Self-closing (`/>`) and open/close (`<rect ...></rect>`) tags parse. Double-quoted values, `>` or `/` inside a quoted value, and whitespace around `=` all pass. A real `fill=` is always seen.
- **`fill=` inside another value.** A `fill=` written inside another attribute's value is not counted.
- **Malformed tags.** Unquoted values, and `/ >` (not well-formed XML), fail as `open tag is malformed` and are not skipped.
- **Interplay with the earlier checks.** The paint regex and the `ICON_ATTRS` scan are not quote-aware, but text inside a value can only add matches to them, which makes them stricter. A prior paint match can never swallow a real `fill`, because its captured value must be exactly `none` or a hex.
- **Edge-case values.**
  - `fill=''` is rejected by the paint check.
  - `fill='none'` is admitted, which matches the "declare your own fill" policy.
  - A duplicate `fill`, or mixed quotes such as `fill="#0b0420'`, is either rejected by the paint check or is not well-formed XML. Not well-formed XML gives a broken image, not black paint.
- **Shape list.** `ICON_SHAPES` covers every painting element in `ICON_ELEMENTS`. `svg` and `g` do not paint.

**Open gaps:**
- **WR-01 is closed in form but not in effect.** The fill check only asks whether a `fill` attribute is present. The paint check's `.trim()` accepts a value that the browser then throws away, so a shape can still paint SVG's initial black (WR-01 below).
- **IN-01 is only partly closed.** A `%` followed by two hex digits that do not form valid UTF-8 (for example `%FF`) still makes `decodeURIComponent` throw a bare `URIError` (IN-01 below).

**Necessity:** I read the rubric (`necessity-review.md`). There are no necessity findings. The `open tag is malformed` branch can be reached (a test row covers it), and the earlier text checks are deliberate defense in depth.

## Warnings

### WR-01: A shape can still paint SVG's initial black. A fill value padded with non-ASCII whitespace passes the gate, but the browser rejects it.

**File:** `src/render/asset-free.test.ts:271-276` (paint check, `.trim()` at line 272), `305-315` (fill check, which only tests that the attribute is present), `337` (`ICON_HREF_CHARS`)

**Issue:**
- **How the paint check reads the value.** It normalizes it with `String.prototype.trim()`. That strips all Unicode whitespace: U+00A0, U+FEFF, U+3000, U+2000-200A, U+2028/2029 and others.
- **How the browser reads it.** It parses the `fill` presentation attribute as a CSS value. CSS whitespace is only space, tab, LF, CR and FF, so `'\u00A0#f72585'` is an invalid color. The browser drops the attribute and the shape falls back to the initial fill, black.
- **How the payload gets in.** All of these characters can reach the decoded SVG through `ICON_HREF_CHARS`, which admits any `%XX` (`%C2%A0`, `%EF%BB%BF`, `%E3%80%80`). They are legal XML characters inside an attribute value, so the SVG is still well-formed.
- **The result.** The shape declares a `fill`, so 09fb06f's new presence check is satisfied. The value trims to a palette hex, so the paint check passes. The shape renders `#000000`. This is the exact outcome WR-01 set out to prevent, and it breaks the promise at lines 15-19 ("every shape declaring its own fill (SVG's default fill is black ...)").

**Evidence:**
- **The gate passes these.** A scratch copy of `stripProceduralIcon(iconLink(...))` returned PASS for each of these, added to `GOOD_SVG`:
  ```
  <rect width='32' height='32' fill='\u00A0#f72585'/>
  <rect width='32' height='32' fill='#f72585\uFEFF'/>
  <circle cx='16' cy='16' r='12' fill='\u3000none'/>
  ```
- **The browser paints them black.** I rendered them as `<img src="data:image/svg+xml,...">` in headless Chrome:
  - the control, `fill='#f72585'`, paints magenta;
  - the NBSP and BOM rects paint solid black squares;
  - the U+3000 `none` circle paints a black disc.

**Fix:** Allow only ASCII escapes in the href, so the decoded SVG can hold no non-ASCII character at all. This also closes IN-01 below, because `decodeURIComponent` can no longer throw. And stop trimming beyond XML/CSS whitespace, so the paint check reads what the browser reads:
```ts
// line 337: `%` only as an ASCII escape (%00-%7F); the favicon needs no non-ASCII.
const ICON_HREF_CHARS = /^(?:[A-Za-z0-9\-_.!~*'() =/:]|%[0-7][0-9A-Fa-f])*$/;

// line 272: strip only the whitespace CSS itself strips, not Unicode's.
const value = (m[3] ?? "").replace(/^[ \t\n\r]+|[ \t\n\r]+$/g, "").toLowerCase();
```
Add negative rows, for example:
```ts
["a fill padded with NBSP", withElement("<rect width='32' height='32' fill='\u00A0#f72585'/>"), "outside ICON_HREF_CHARS"],
["a fill padded with a BOM", withElement("<rect width='32' height='32' fill='#f72585\uFEFF'/>"), "outside ICON_HREF_CHARS"],
```

## Info

### IN-01: A well-formed `%XX` escape that is not valid UTF-8 still throws a bare `URIError`, contrary to the new docstring

**File:** `src/render/asset-free.test.ts:333-337` (docstring and pattern), `373` (`decodeURIComponent`)

**Issue:**
- **What 735a50b closes.** A lone `%`, `%z`/`%zz` and a truncated `%4` now fail with the gate's own message.
- **What it misses.** `%[0-9A-Fa-f]{2}` still admits escapes that are not valid UTF-8, so `decodeURIComponent` throws `URIError: URI malformed`. Three examples:
  - `%FF`, which is never a valid UTF-8 byte;
  - `%C3%28`, a lead byte followed by a byte that cannot continue it;
  - `%ED%A0%80`, an encoded surrogate.

  I confirmed all three in a scratch copy. Each one passes `ICON_HREF_CHARS` and then throws the bare error.
- **Why it matters.** The docstring at lines 333-335 says the bare `URIError` "now fails here with this gate's own message", which is not true for this class of input. The new test rows only cover cases where the `%` is not followed by two hex digits. The gate still fails closed, so only the message is affected.

**Fix:** Use the ASCII-only escape pattern from WR-01 (`%[0-7][0-9A-Fa-f]`), which makes `decodeURIComponent` unable to throw. Add a `%FF` row to the bad-escape `it.each` at lines 623-627. If non-ASCII escapes have to stay, wrap the decode instead:
```ts
let decoded: string;
try {
  decoded = decodeURIComponent(raw);
} catch {
  throw new Error("icon href holds a % escape that is not valid UTF-8");
}
validateIconSvg(decoded);
```
