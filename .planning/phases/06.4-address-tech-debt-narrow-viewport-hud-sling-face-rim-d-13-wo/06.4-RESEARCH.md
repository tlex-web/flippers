## Summary

**HUD.** Today the canvas is fitted to the whole window (`computeView(bounds, window.innerWidth, window.innerHeight, dpr)`), centered by `#sandbox` flex, and the HUD is a `position: fixed` panel at top-left 16 px. There is no `@media` rule. The table box is 3.66 x 6.65 m (aspect 0.558), so whenever the table binds on height, the canvas left edge sits at `(vw - 0.536 vh) / 2`. The panel (about 268 px wide, so its right edge is at about 284 px) clears that only when `vw >= ~600 + 0.536 vh`. The condition depends on both width and height (1080x1080 overlaps, 1024x768 does not), so **a width-only `@media` breakpoint cannot be correct**. Recommendation: **"side when it clears, top bar when it doesn't."** On each resize, main.ts measures the side panel's right edge, keeps today's layout when the canvas clears it, and otherwise sets `data-hud="bar"` on `#sandbox`. CSS then turns the HUD into an in-flow, 3-row bar above the table (score, ball/best, status, plus the Mute row; the controls list, the Windows note and the dev readout are hidden). The canvas is fitted to the height left under the bar. At 375x812 the table keeps its full size (it binds on width and there are 166 px spare). At 768x1024 it shrinks about 11% (549x983 to 490x877) and is fully visible.

**Sling rim.** `drawSlingshot` fills the triangle with SLING_BODY `#2b2d42` and strokes only the kick face (segment `el.kickFace`, which is 2) in SLING_RUBBER. Add one stroke over every other segment (0: the inlane face, 1: the lower face) before the rubber, in a new palette constant `SLING_RIM = "#7d82a8"` (the body's slate hue, lightened) at `SLING_RIM_LINE_M = 0.015` m (half of RUBBER_LINE_M). Measured contrast against the playfield behind the sling is **4.6:1**, up from 1.28:1. That passes the WCAG 1.4.11 3:1 non-text floor and stays below the rubber (9.9:1) and the walls (9.0:1). The bake is not on the physics path. Determinism replays compare world state, and the bake reads only `el.segments`/`el.kickFace`, so they cannot move.

**D-13.** Five text sites need changing: one CONTEXT line, the root-shot header doc, the `FlipResult` doc, the describe title and the it title. Two optional ledger notes go with them (06.3-REVIEW-DISPOSITION IN-01 → fixed, and the STATE.md blocker line). No assertion changes.

### Pattern 1: Pure layout predicate beside `computeView`

**What:** Two tiny pure exports in `src/render/view-transform.ts`, unit-tested like `computeView`.
**Example (recommended shape; names are proposals, [ASSUMED]):**
```typescript
/** Gap (CSS px) the side HUD panel keeps from the canvas (06.4). */
export const HUD_SIDE_GAP_CSS = 16;
/** Gap (CSS px) between the top HUD bar and the canvas; equals `gap` on #sandbox[data-hud="bar"] in index.html. */
export const HUD_BAR_GAP_CSS = 8;

/** Whether a side panel whose right edge is at `panelRight` CSS px clears the centered canvas. NaN → false (bar). */
export function sideHudClears(view: ViewTransform, viewportW: number, panelRight: number): boolean {
  return (viewportW - view.cssW) / 2 >= panelRight + HUD_SIDE_GAP_CSS;
}

/** Viewport height left for the table under a top HUD bar `barH` CSS px tall. */
export function heightUnderBar(viewportH: number, barH: number): number {
  return viewportH - barH - HUD_BAR_GAP_CSS;
}
```
`computeView` already clamps a viewport side below 1 to 1, so `heightUnderBar` needs no guard [VERIFIED: src/render/view-transform.ts:106-109 `return Number.isFinite(v) && v >= 1 ? v : 1;`].

### Pattern 2: main.ts glue (replaces `applyView` body)

Current code [VERIFIED: src/sandbox/main.ts:367-375]:
```typescript
    const bounds = tableBounds(world.getElements());
    const applyView = (): void => {
      tr.resize(
        computeView(bounds, window.innerWidth, window.innerHeight, window.devicePixelRatio || 1),
      );
    };
    applyView();
    window.addEventListener("resize", applyView);
```
Recommended:
```typescript
    const sandbox = requireElement("sandbox");
    const hud = requireElement("hud");
    const applyView = (): void => {
      const vw = window.innerWidth;
      const vh = window.innerHeight;
      const dpr = window.devicePixelRatio || 1;
      sandbox.setAttribute("data-hud", "side"); // measure the panel in its side form
      const full = computeView(bounds, vw, vh, dpr);
      if (sideHudClears(full, vw, hud.getBoundingClientRect().right)) {
        tr.resize(full);
        return;
      }
      sandbox.setAttribute("data-hud", "bar");
      tr.resize(computeView(bounds, vw, heightUnderBar(vh, hud.getBoundingClientRect().height), dpr));
    };
```
The existing resize listener and dpr `matchMedia` re-arm keep calling `applyView` unchanged [VERIFIED: src/sandbox/main.ts:375-387]. `requireElement` is a hoisted function declaration at the bottom of main.ts [VERIFIED: src/sandbox/main.ts:585-589]. Use `setAttribute`, not `dataset.hud`. Both type-check, but `setAttribute` matches the HUD's `AttrSink` idiom.

### Anti-Patterns to Avoid
- **A width-only `@media (max-width: 900px)` breakpoint.** Overlap depends on `vw − 0.536·vh`, so it misfires both ways (1080x1080 overlaps; a 880x500 window would be forced into the bar for nothing). Use the measured predicate. CSS still holds all the styling.
- **ResizeObserver on `#hud`.** Not needed (bar height is constant by design) and it risks the "ResizeObserver loop" error because `applyView` flips the attribute side→bar inside the callback.
- **`display: contents` on the `<dl>`** to pull the mute marker into the bar grid. It has a history of dropping list semantics in the accessibility tree. The `:nth-last-child` hide keeps the `<dl>` intact.
- **Hiding the HUD or shrinking fonts below 12 px.** The 11 px floor debt is separate. Don't add more.
- **Rim in SLING_RUBBER, WALL or any existing meaning color.** The palette header says "One meaning per color" [VERIFIED: src/render/palette.ts:1-7]. Amber means "kicks" and cyan means "guide wall".

## Sling Rim (item 2)

Current code [VERIFIED: src/render/static-layer.ts:283-295]:
```typescript
function drawSlingshot(ctx: CanvasRenderingContext2D, el: ResolvedElement): void {
  traceElement(ctx, el);
  ctx.fillStyle = SLING_BODY;
  ctx.fill();
  const face = deriveKickFace(el);
  if (!face) return;
  ctx.beginPath();
  ctx.moveTo(face.ax, face.ay);
  ctx.lineTo(face.bx, face.by);
  ctx.strokeStyle = SLING_RUBBER;
  ctx.lineWidth = RUBBER_LINE_M;
  ctx.stroke();
}
```
How the kick face is known: `ResolvedElement.kickFace: number | null` [VERIFIED: src/table/resolve.ts:59-60 `readonly kickFace: number | null;`]. `deriveKickFace` reads `el.segments[el.kickFace]` [VERIFIED: src/game/reactive-elements.ts:178-179 `const face = el.kickFace === null ? undefined : el.segments[el.kickFace];`]. Both slings use `kickFace: SLING_KICK_FACE` with `const SLING_KICK_FACE = 2;` [VERIFIED: src/table/spec.ts:308, 405-411]. Left sling vertices [VERIFIED: src/table/spec.ts:297-301]: `{ x: 0.86, y: 3.85 }`, `{ x: 0.86, y: INLANE_Y }` (`INLANE_Y = 4.6`, :282), `{ x: 0.944, y: 4.102 }`. Segment 0 = inlane face (vertical), segment 1 = lower face (the root-shot face), segment 2 = kick face.

Palette [VERIFIED: src/render/palette.ts:10-13 `BG_TOP = "#05061a"`, `BG_BOTTOM = "#0b0420"`; :37-40 `SLING_BODY = "#2b2d42"`, `SLING_RUBBER = "#ffb703"`; :116-124 `WALL_LINE_M = 0.014`, `RUBBER_LINE_M = 0.03`]. `bakeStatic` sets `lineCap = "round"` and `lineJoin = "round"` before the element loop [VERIFIED: src/render/static-layer.ts:422-423].

**Recommended spec:**
- New constants in palette.ts (proposals, [ASSUMED] names):
  - `/** Slingshot rim on the passive (non-kick) faces: SLING_BODY's slate hue, lightened (06.4). */ export const SLING_RIM = "#7d82a8";`
  - `/** Slingshot passive-face rim (half of RUBBER_LINE_M). */ export const SLING_RIM_LINE_M = 0.015;` placed in the line-width block.
- Edges: every segment index `!== el.kickFace` (on today's slings, segments 0 and 1). The rim is drawn after the body fill and **before** the rubber, so the rubber's round caps sit on top at the two shared corners.
- Implementation sketch:
```typescript
  // Passive-face rim (06.4): every segment but the kick face, under the rubber.
  ctx.beginPath();
  const segs = el.segments;
  for (let i = 0; i < segs.length; i++) {
    if (i === el.kickFace) continue;
    const s = segs[i];
    if (!s) continue;
    ctx.moveTo(s.a.x, s.a.y);
    ctx.lineTo(s.b.x, s.b.y);
  }
  ctx.strokeStyle = SLING_RIM;
  ctx.lineWidth = SLING_RIM_LINE_M;
  ctx.stroke();
```
  Separate subpaths with round caps look identical to a round join at the shared vertex, and the loop handles any segment count. Keep the existing `if (!face) return;` for the rubber.
- On-screen width: 0.015 m × 400 px/m × fit = 1.9 CSS px at 1440x900 (fit 0.319), 1.4 px at 375x812 (fit 0.238), 2.0 px at 768x1024 bar (fit ≈ 0.324) [VERIFIED: `PIXELS_PER_METER = 400`, src/physics/constants.ts:77; fit from the probe]. That is at least 1 device px everywhere, comparable to the 0.014 m walls. The ball radius is 0.2 m [VERIFIED: src/physics/constants.ts:48], so the 7.5 mm the stroke reaches past the collider is invisible as a gap.

## Common Pitfalls

### Pitfall 1: Bar height changes without a resize
**What goes wrong:** The status, best or MUTED text changes the bar height, and the canvas then overflows or shifts, because no resize event re-fits it.
**How to avoid:** Fixed rows. Ball and best share one cell; `.hud-status` keeps `min-height: 1.2em`; the Mute row is always present (only "MUTED" empties; `:empty` sets it to display none, the key cap stays). Test by toggling M and starting/ending a game at 375 in the UAT.

### Pitfall 2: Canvas comes first in DOM
**What goes wrong:** In column flex the bar renders **below** the table.
**How to avoid:** `order: -1` on `.hud` in bar mode. Fixed children (`#hud-bonus`, `#hud-diag`) are out of flow, and so is the absolutely positioned `.visually-hidden` live region.

### Pitfall 3: Flex shrinks the canvas
**What goes wrong:** `#stage` is a flex item with an explicit px size. If the group exceeds the container, `flex-shrink: 1` squeezes it and the CSS size no longer matches the backing (blurry or stretched).
**How to avoid:** `#stage { flex: none; }`.

### Pitfall 4: `100vh` on mobile
**What goes wrong:** `vh` equals `lvh`, so with the URL bar visible the vertically centered group sits about half the toolbar height too low and the apron or plunger is clipped [CITED: MDN length, "vh is equivalent to lvh"].
**How to avoid:** `min-height: 100vh; min-height: 100dvh;` (fallback first). The fit already uses `innerHeight`. The page never scrolls, so dvh's resize-on-scroll caveat does not apply.

### Pitfall 5: Measuring in the wrong mode
**What goes wrong:** Reading the panel's right edge while `data-hud="bar"` (it would be the full width) or the bar height while in side mode.
**How to avoid:** Set the attribute, then read `getBoundingClientRect()` (the read forces a synchronous layout; it runs only on resize or dpr change, never per frame, and there is no paint between the flips). Read the bar **height**, not its `bottom`, because `bottom` depends on the stale canvas size under `justify-content: center`.

### Pitfall 6: The debug renderer path
`?debug=1` sizes through `DebugRenderer.resize(world)` and never calls `applyView` [VERIFIED: src/sandbox/main.ts:344-349]. It keeps the side layout. That is acceptable for a dev-only mode; state it in the main.ts header.

### Pitfall 7: The rim under the rubber, not over it
If the rim strokes after the rubber, its caps at the two kick-face corners nick the amber ends. Order: fill, rim, rubber.

### Pitfall 8: The test-title rename breaks a `-t` filter
Only historical, completed plans use `-t "clears its own sling"`. New verification commands must use the new title or run the file whole.
