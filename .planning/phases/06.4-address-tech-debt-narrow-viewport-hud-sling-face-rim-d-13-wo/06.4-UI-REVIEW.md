## Top 3 Priority Fixes

1. **Bar mode hides every control hint except Mute, with no touch alternative** (WARNING). The DOM check confirmed that in bar mode the attract status line reads "PRESS ENTER TO START", so the start key is still named. The plunger key (Space) and the flipper keys are not shown anywhere on 768x1024 or 375x812, and the game is keyboard-only. The hiding rule is index.html:99-109: `.hud-controls > :not(:nth-last-child(-n + 2))` and `.hud-controls-note` get `display: none`. Fix: show one compact line in the status row in the ready state, for example "Hold Space to launch · ← → flip". The keys come from index.html:357-366. Alternatively, show the controls only in the READY and attract states. The user approved A3 at UAT, so treat this as a follow-up, not a regression.
2. **The 11 px label type stays below a comfortable floor** (WARNING, known debt carried since 04). It is at index.html:128, :252 and :311 (`.hud-label`, kbd caps, bonus heading). In the 375x812 capture the 11 px SCORE label and the "Mute [M]" key cap are the faintest text in the bar. Fix: raise labels to 12 px, which the scale already uses, so the type scale shrinks by one size.
3. **`/favicon.ico` still returns 404** (WARNING, portfolio polish, carried from 06.2). It is the only console error on a clean boot in the MCP pass, and index.html has no `<link rel="icon">`. Fix: add a procedural SVG data-URI icon in index.html `<head>`, which needs no asset file.

Minor recommendations:
- **Bar width is full width, not table width.** This was a user-approved choice at the 06.4 UAT (06.4-04-SUMMARY.md:150-154), so it is not a defect. Measured at 768x1024, the bar spans x 8-760 (752 px) and the canvas spans x 138-630 (491 px). At 1000x1000 the bar is 984 px over a 478 px canvas. If it is ever revisited, 06.4-RESEARCH Open Question 1 already gives a fallback that avoids a circular measure: `max-width: 560px; align-self: center`.
- `.hud-bonus` is `position: fixed` at screen center (index.html:281-287) with a 240 px minimum width. In bar mode it overlays the table by design. The UAT confirmed it clears the bar at 375. Keep it as a regression check if the bar height changes.
- The bar's `margin: 0 8px` and `gap: 8px` are duplicated between CSS and the TS constant `HUD_BAR_GAP_CSS` (src/render/view-transform.ts:56). A comment documents the link and a test reads index.html, which is acceptable.

## Detailed Findings

### Pillar 1: Copywriting (3/4)
- No user-visible string was added or changed in 06.4. Plan 03 was a docs and test-title change only. The root-shot.test.ts titles now say "first contact".
- Deduction: the bar layout hides the keyboard list and the Windows note (index.html:99-109). On a narrow viewport the player is shown SCORE, BALL, status and Mute only. The DOM check confirmed the attract status line names the start key ("PRESS ENTER TO START"), and the line fits on one row even at 320x568 (scrollWidth equals clientWidth, 279 px). Plunger and flipper keys are not shown.

### Pillar 2: Visuals (4/4)
- The 06.2 top fix 1 (the sling lower face is nearly invisible, about 1.28:1) is addressed in code. static-layer.ts:293-301 adds a slate stroke on faces 0 and 1 (inlane face and lower face) under the amber kick face. The palette gives SLING_RIM `#7d82a8` (palette.ts:42) and a 0.015 m width (palette.ts:128). Research measured 4.6:1 against the playfield. The stroke is a single batched path with no per-frame cost, since it is baked once per resize.
- The kick face remains the only amber edge, so the kick and passive faces read differently. The rim does not change the kick zone (06.3 IN-03 stays out of scope).
- Bar mode keeps one focal point. The 32 px score is the largest element, and the label/aux row and status row sit at 11, 16 and 12 px.
- Pixel evidence (orchestrator MCP pass, `.planning/ui-reviews/06.4-mcp/tablet-play.png` and `mobile-play.png`): both slings show a thin slate edge on the inlane face and the lower face under the amber kick face. The lower face, which was nearly invisible in 06.2, now reads clearly against the playfield at both 768x1024 and 375x812. The bar shows SCORE / BALL 1 / 3 on row 1, the 32 px score with "Mute [M]" on row 2, and an empty status row during play. It has one focal point. The draft's only deduction was the missing pixel evidence, so it is lifted.

### Pillar 3: Color (4/4)
- A single new constant, SLING_RIM, is used once (static-layer.ts:299). There are no hardcoded colors in the new bar CSS, which uses the existing `--text`, `--label`, `--status` and `--panel-bg` variables.
- The accent stays reserved: magenta `--status` for the status line, cyan for walls and glow. The 60/30/10 split is unchanged.
- Rim contrast of 4.6:1 passes WCAG 1.4.11 and stays under the rubber (9.9:1) and walls (9.0:1), so the hierarchy holds.

### Pillar 4: Typography (3/4)
- index.html uses four sizes (11, 12, 16 and 32 px) and two weights (400 and 700), unchanged by this phase.
- Deduction: 11 px labels (index.html:128, :252, :311) are still the smallest type, and the narrow bar is where they matter most.
- The bar sets `line-height: 1.25` and `1.2` with matching `min-height` (index.html:87-98), so the bar height stays constant across attract, ball and best states. This is a solid detail.

### Pillar 5: Spacing (4/4)
- This phase resolves 06.2 top fix 2. The decision is measured, not width-based. main.ts:386-392 sets side mode, measures `#hud.getBoundingClientRect().right`, and calls `sideHudClears` (view-transform.ts:165). If the panel does not clear the canvas by HUD_SIDE_GAP_CSS (16 px), it sets `data-hud="bar"` and refits the table under `heightUnderBar` (view-transform.ts:173).
- A width-only `@media` rule would be wrong because the overlap depends on both axes (1080x1080 overlaps and 1024x768 does not). The research proves this, and the implementation handles it.
- The bar uses `margin: 0 8px; padding: 8px 12px; gap: 8px` (index.html:61-70), all on the 4 px grid. Per 06.4-RESEARCH, the table shrinks about 11% at 768x1024 and keeps full size at 375x812.
- Measured: the gap from the bar's bottom to the canvas's top is exactly 8 px at 1000x1000, 768x1024, 375x812 and 320x568. No viewport has page overflow (scrollWidth/scrollHeight equal the viewport). At 1440x900 the side panel's right edge (x 284) clears the canvas (x 478) by 194 px.

### Pillar 6: Experience Design (3/4)
- The layout switches live on resize and boot. The layout reads are limited to resize, and the pure predicates have unit tests (src/ui/hud-layout.test.ts, view-transform.test.ts). The bar has a constant height, so the table does not jump when Enter or M changes the HUD text.
- The status line keeps `role="status"` and `aria-live="polite"` (index.html:355). DOM and reading order are unchanged, because the bar uses CSS `order: -1`.
- Deduction: control hints are removed in bar mode with no replacement (Top fix 1). On a phone there is still no touch input, which stays out of scope per the research.
- Gate evidence is strong: 1357 tests, soak 4/4 and byte-identical sim directories.
- Measured: at 1000x1000 the bar is 102 px tall and the canvas top is at y 127, both before and after Enter. The HUD went from attract (status "PRESS ENTER TO START", ball empty) to play (ball "BALL 1 / 3", status empty), so the table does not move when the game starts.
